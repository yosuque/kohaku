# 0007. The composer deterministically injects L1 filters from the Intent's facet declarations

- Status: accepted
- Date: 2026-11-08
- Deciders: yosuque + Claude Code
- Phase: design

## Context and problem

L0 (fixed) screens can swap their data without re-composing and without a model call, through the structured sidecar `data.bind` (design.md #13). Screens generated by the model (L1) had no such filters; design.md #13 left "opening to L1" as a future task, with the condition that it be done without letting the model write binds. The reason is authorization: a bind's value domain decides which read scopes the capability carries, so the model must not decide it. The maintainer confirmed this on 2026-11-08: filters are injected from the Intent's facet declarations, and the model emits none.

## Options considered

- **Option A**: the composer injects filters deterministically from the Intent definition's facet declarations (chosen).
- **Option B**: let the model emit filters and binds in L1 generation. Rejected by the premise above: the model would decide the authorized range.

Choices inside Option A that had a recorded alternative:

- **Re-issuing the capability**: the implementation plan assumed a re-issue "on the final spec event". The L1 stream has no such event (`skeleton → patch* → done`), so the replacement rides the last convergence patch instead.
- **Variant cap**: 64 or 256 (see Decision).

## Decision

Chosen: **Option A**

- **Opt-in**: `ComposePolicy.l1Filters`, default off. Enabled in the TS and Python sales samples.
- **Descriptors**: spec-core gains `FilterDescriptor { param, queryParam, paths, label, options }` and an optional `SemanticPort.describeFilters(intent, { tenant, locale })`. `@kohaku-ui/intents` derives them from the facets in `IntentDef.filters(locale)`. Only discrete-string `select` facets qualify. A filter is excluded when its `queryParam` appears in a template's `fixedParams` or is shared with another param on the same path.
- **Injection**: composer's `injectFilters` runs after `normalizeIds`. For each descriptor whose `queryParam` appears in a data `$ref` on one of its `paths`, it adds a `control.select`, its `state`, a `state.set` event, and `data.bind` on those components only. Nothing is injected when the current value is not one of the options. If the result is not a valid Spec, the original Spec is delivered as generated.
- **Cache key**: a hash of the descriptors actually used (labels, options, paths) is part of the policy fingerprint, so tenants, locales and option changes never share a cached Spec.
- **Locale**: labels follow `session.locale` (`ja-JP` falls back to `ja`).
- **Variant budget**: `ComposePolicy.l1FiltersMaxVariants`, default 64, included in the fingerprint. Over the cap, injection is skipped (`variant-limit`).
- **Capability**: the read scopes come from the variants actually injected. On the stream, the last converging `patch` event may carry a replacement `capability` and `actions` manifest, only when the final Spec has `data.bind` (SPEC §6.1.1, additive on the wire).
- **MCP initial data**: pre-resolves every initial ref plus at most 32 deduplicated non-initial variants. This applies regardless of `l1Filters`, and the gated-read guard of [ADR-0006](0006-data-plane-read-path-never-runs-gated-operations.md) applies to each variant.
- **Mirror**: Python implements all of it; the cross-language golden pins `injectFilters` (22 cases), the descriptor hash and the fingerprint (14 cases).

### Rationale

- The filter set is a deterministic function of the Intent definition, and the generation schema stays sealed, so the model cannot influence the injected `bind`, `state`, `control.select` or `values`. The wp-o1 review confirmed this.
- The descriptors decide the authorized range and the label language, so they belong in the cache key; otherwise a tenant- or locale-specific Spec would be served across tenants and locales.
- 64, not 256, because a 256-scope capability is about 35 KB and exceeds Node's 16 KiB header limit, so `/binding/resolve` would answer 431.
- Each filter is scoped by `paths`, and an ambiguous filter is excluded, so a `queryParam` never silently changes the meaning of a ref it was not declared for.

## Consequences (trade-offs)

- Good: filters on L1 screens swap data with no extra compose call and no model call (sample e2e, TS and Python). Closes design.md #13's "opening to L1". Other streams are byte-identical to before.
- Costs / bad:
  - **A selected value cannot be cleared back to "all".** There is no empty bind value, the same limitation as the L0 cross-filter. Fixing it needs a `data.bind` protocol extension (an empty value removes the query parameter), which is out of scope.
  - Only discrete-string `select` facets qualify, and an ambiguous filter is dropped rather than guessed.
  - A Spec that would need more than 64 variants is delivered without filters.
  - The MCP initial-data change (up to 32 extra variants) applies to every Spec, not only those with filters.
- Revisit when: a `data.bind` extension for clearing a selection is taken up (recorded as a follow-up and ADR candidate in wp-o1).
