# 0021. CI はランタイムごとに 1 バージョンだけ検証し、それを下限として表明する

- ステータス: accepted
- 日付: 2026-11-10
- 決定者: yosuque + Claude Code
- フェーズ: 運用

## コンテキストと課題

CI は Node 24 と 26、Python 3.12 と 3.13 で実行していた。表明していた最低要件は `engines.node >=24.22.1`(公開する全パッケージ、root のマニフェスト、`kohaku init` のプロジェクト)と `requires-python >=3.12` である。これらの下限は ec723342 で、「表明する下限は CI が実際に実行するバージョンでなければならない」という原則に基づいて決めた。

メンテナは CI のバリエーションを減らしたかった。下限を据え置いたまま下側の実行だけを外すと、この原則が崩れる。しかも、その穴を埋めるものが他になかった。

- catalog の `@types/node` は `^26` なので、Node 26 にしかない API を使っても `tsc` は検出しない。それを捕まえていたのは Node 24 でのテスト実行だけだった。
- Python は、ruff(`target-version`)と mypy(`python_version`)が 3.12 の下限を静的に検査していた。3.12 での実行に残っていた役割は、実行時の挙動の確認だけだった。

これまでの実績を見ると、追加の実行が直接役立ったことはほとんどない。2026-10-17 以降の 150 回の CI 実行(失敗 9 回)で、特定のバージョンだけが落ちた失敗は 1 件もなかった。一方で、追加の実行が全体の待ち時間を延ばしていたわけでもない。`ci (24)` は 158 秒、`ci (26)` は 277 秒だった。

## 検討した選択肢

- **A. 言語ごとに 2 バージョンを維持する。** 失うものはないが、チェック一覧は長いまま。
- **B. 下限バージョンの実行を PR から外し、`main` への push と夜間だけで回す。** 検証範囲は残るが、下限での問題に気付くのがマージ後になる。`ci-ok` がスキップされたジョブを受け入れるよう直す必要もある。
- **C. 下限を CI に残すバージョンまで引き上げ、その 1 バージョンだけを検証する。** 古いランタイムの利用者にとっては破壊的変更。
- **D. Python だけ 1 バージョンにし、下限は静的検査で守る。** 影響は小さいが、Node は変わらない。

C の中で、Node の扱いには 2 通りあった。メジャー版で浮かせる方法(`node-version: 26`。最新の 26.x で走り、下限の `>=26.0.0` は検証されない)と、CI を 1 つの正確なバージョンに固定して `>=` その版を表明する方法である。

## 決定

採用: **C。Node は正確なバージョンに固定する**(PR #138)。

- **方針。** CI は Node と Python をそれぞれちょうど 1 つのバージョンで実行する。表明する下限(`engines.node`、`requires-python`)はそのバージョンとし、それより古い版も新しい版も検証しない。下限は判断して引き上げる。少なくとも Node の新しい LTS 系列や Python の新しいマイナーバージョンが出たときに見直し、引き上げは破壊的変更として changeset に記録する(0.x の間は `minor`)。CONTRIBUTING.md §2 に明記した。
- **Node: `.node-version` を唯一の記録元とし、現在は 26.12.1。**
  - 全ワークフローの setup-node が `node-version-file: .node-version` を使う。
  - `scripts/lib/node-floor.mjs` がこのファイルから `>=26.12.1` を導く。`pnpm meta:sync` がそれを公開する 30 パッケージと root の `package.json` に書き、`pnpm init:versions` が `kohaku init` のプロジェクト用に `NODE_ENGINES` として書き出す。
  - どれかが `.node-version` とずれると、テストと CI のずれ確認で失敗する。
- **Python: 3.13。** 3 つの pyproject の `requires-python >=3.13`、classifiers、ruff の `py313`、mypy の `3.13`。CI は ci.yml の `PYTHON_VERSION: "3.13"` を使い、release.yml と published-e2e.yml も同じバージョンにする。1 つのファイルにまとまっていないので、変更すべき箇所を CONTRIBUTING.md に列挙した。

### 理由

- ec723342 の原則を保ったまま、メンテナが減らしたかったバリエーションを減らせる。CI が実行していないことは約束しない。
- 固定すると、「CI が検証するバージョン」と「表明する下限」が文字どおり同じ値になる。下限の引き上げは、`.node-version` を書き換える、`pnpm regen` を実行する、init の golden を再生成する、ドキュメントを直す、changeset を足す、という手順になる。
- B は問題に気付くのをマージ後に遅らせ、集約ジョブも複雑にする。D は効果の小さい半分しか解決しない。
- Node 26 は 2026 年 10 月から Active LTS である。Python 3.13 は、このリリース系列の期間を大きく超えて上流のサポートが続く。

## 結果(トレードオフ)

- **良い点:**
  - ランタイムごとに 1 バージョンになり、Node の下限は 1 つのファイルから生成される。
  - [ADR-0020](0020-ci-ok-is-the-single-required-ci-check.ja.md) に加えて、PR 1 件あたりのチェックが 10 個から 8 個に減った。
  - パッケージが表明する内容と、CI が検証した内容が一致する。
- **コスト・悪い点:**
  - Node 24(上流のサポートは 2028-04 まで)や Python 3.12 の利用者は、このリリースを入れる前にランタイムを上げる必要がある。
  - より新しいランタイムは検証されない。`.node-version` を上げるまでの Node 26 の新しいパッチ、Node 27 以降、Python 3.14 以降がそれに当たる。uv.lock は 3.14 用に別の依存の組み合わせを解決しているが、CI はそれを一度も実行しない。
  - Python の下限は、今後も複数のファイルを手で変更する必要がある。
- **見直す条件:** Node の新しい LTS 系列や Python の新しいマイナーバージョンが出たとき。利用者が古いランタイムを必要としたとき。下限より新しいランタイムでしか再現しない不具合が出たとき。最後の場合は方針を捨てるのではなく、マージを止めない 2 つ目の実行を追加する。
