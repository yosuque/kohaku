# 0001. アーキテクチャ上の判断を ADR として記録する

- ステータス: accepted
- 日付: 2026-11-08
- 決定者: yosuque + Claude Code
- フェーズ: 運用

## コンテキストと課題

要件定義・設計・実装の過程で「なぜそうしたのか」という判断の理由は、時間が経つと失われやすい。特に Claude Code と協働で開発を進める場合、判断の経緯がチャット履歴に埋もれ、後から追跡できなくなる。このリポジトリではこれまで、実装上の判断を [design.ja.md](../design.ja.md) の判断記録とコミットメッセージ・PR 説明に残してきたため、依存の更新方法のような運用上の方針には置き場所がなかった。判断の文脈・選択肢・トレードオフを、コードと同じリポジトリで永続化したい。

## 検討した選択肢

- **選択肢A**: ADR を `docs/adr/` に MADR 形式で残し、Git で版管理する
- **選択肢B**: Wiki / 外部ドキュメントツールに残す
- **選択肢C**: 記録しない(コミットメッセージと PR 説明に留める)

## 決定

採用: **選択肢A(MADR 形式の ADR を `docs/adr/` に置く)**

### 理由

- コードと同じリポジトリに置くことで、変更履歴と判断履歴が一元的に追跡できる
- Markdown のプレーンテキストで、ツール非依存・差分が読みやすい
- 連番ファイルで一覧性・参照性が高い(ADR-NNNN で相互参照可能)

## 結果(トレードオフ)

- 良い影響: 判断の理由が永続化され、オンボーディングや再検討が容易になる
- 受け入れるコスト: 判断のたびに ADR を書く運用負荷(`/adr` スキルで軽減)。`docs/` はドキュメントサイトに反映されるため、ADR ごとにサイドバーへの登録が要り、リポジトリの規約に従って英語の正本と `.ja.md` の両方を書く必要がある
- 見直し条件: 運用が形骸化した場合、対象範囲(どの粒度の判断を残すか)を再定義する
