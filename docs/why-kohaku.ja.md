# なぜ kohaku か

[English](why-kohaku.md) | 日本語

kohaku は「画面を速く生成する」ためのものではありません。LLM が生成した UI を**統制のもとで本番に載せる**ためのものです。同じ要求は必ず同じ画面になり、モデルはデータに触れず、モデルが発明したものはレビューを通るまで製品の一部になりません。

Generative UI を「モデルがどれだけ速く何かを描けるか」で評価するなら、多くのツールは似たように見えます。kohaku はデモの後に来る問いのために作られています。*明日も同じものが表示されるか? 何を表示したか監査できるか? モデルが間違えたらどうなるか?*

## 3 つの保証

### 1. 同一表示は統計ではなく構造で保証する

チャットの質問も GUI の操作も、ひとつの**正規化 Intent**(`sales.quarterly_summary` + ソート済み params)に正規化されます。Intent・データバージョン・部品カタログの指紋が **UI Spec**(コードではなく JSON 文書)のキャッシュキーになります。同じ要求 → 同じキー → バイト単位で同じ Spec が、チャットの吹き出しからでもファセットパネルからでも、どのレンダラー(React、Web Components、MCP Apps のウィジェット)でも返ります。temperature 0 は補助で、キャッシュが保証です。よく使われる画面は L0 に**固定化**され、モデルをまったく通らなくなります。

### 2. モデルが組むのは配管で、水は流れない

Spec が運ぶのは `query://` **参照**だけです。部品は、ホストがその参照に対してだけ発行した短命の capability トークンを使って、あなたの API からデータを直接取得します。モデルをデータの値が通らないので、転記ミスも、プロンプトへの漏洩も、モデル提供者のログに残るあなたのデータもありません。認可と不変条件が住む場所は DomainPort ひとつのままです。

### 3. 自由を許し、そのうえで統制する

カタログ外の要求はサンドボックス(不透明 iframe・CSP・許可リスト付きブリッジ)の中で自由に生成されます(**L2**)。モデルが作ったものは lineage に記録され、十分使われると**昇格候補**になります。任意の LLM 判定器が、人がレビューする前に候補を採点することもできます。人がレビューし(ユーザーが見たものと sha256 で同一の、描画されたアーティファクトそのものを見て)、スキーマを承認します。以後それは型付きの契約を持つ正式な **L1** 部品になり、モデルは再発明する代わりにそれを選びます。統制は後付けではなく製品そのものです。

## kohaku の位置付け

| 必要なもの | 候補 | kohaku の立場 |
|---|---|---|
| プロンプトから使い捨ての画面への最短経路 | プロンプト→コード生成器、"vibe coding" ツール | 目標ではない。kohaku は決定性とレビューに手間をかけるので、最初の一枚は遅い |
| チャット UI の部品ライブラリ | チャット SDK・ウィジェットライブラリ | 補完関係。kohaku はウィジェットの*中身*をデータとして作り、チャットホストが描画する |
| エージェントが UI と話すためのプロトコル | A2UI / AG-UI / MCP Apps | kohaku は今日 MCP Apps を実装し、A2UI 互換プロファイルの骨格を同梱する。Spec がペイロード、プロトコルはトランスポート |
| 毎日同じように振る舞い、監査証跡を持つ生成 UI | **kohaku** | 同一表示 + 参照渡し + 昇格パイプラインを参照実装が備え、TypeScript と Python の両方で conformance 検証済み |

## 使わないほうがよいとき

- 再利用のない自由形式の使い捨て画面が必要 — レビューの手間は回収できない。
- データがプロンプトに入っても安全で、監査証跡も不要 — もっと単純なプロンプト→UI ツールで足りる。
- データに対するクエリ API を公開できない — 参照渡しには部品が呼べるエンドポイントが要る。
