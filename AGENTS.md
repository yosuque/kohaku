# kohaku monorepo — guide for AI coding agents

The reference implementation of "kohaku", an AI-native GUI library. UI is treated as a declarative UI Spec (data), separating generation (composer) from rendering (renderer). Details: [docs/design.md](docs/design.md) (implementation design) and [spec/SPEC.md](spec/SPEC.md) (normative protocol).

## Commands

```bash
pnpm install                 # install dependencies (pnpm 12 / Node >= 22)
pnpm test                    # all tests (Vitest projects; everything passes without an LLM)
pnpm vitest run --project composer   # single-package tests (names come from each vitest.config.ts `name`)
pnpm typecheck               # tsc --noEmit for all packages
pnpm check                   # Biome: format + safe lint fixes + organize imports (writes)
pnpm check:ci                # Biome: verify only (what CI runs)
pnpm build:dist              # emit dist for the 29 publishable packages (same tsc as typecheck; dist is gitignored)
pnpm smoke:pack              # pack every package and verify the tarballs outside the workspace (own CI job)
pnpm meta:sync               # regenerate the publishing metadata / publishConfig (CI checks for drift)
pnpm changeset               # record a version bump for a change (a version PR is opened from main; publishing is a separate, tag-driven step — docs/runbooks/release.md)
pnpm seed                    # regenerate the sales seed (deterministic — regeneration produces no git diff)
pnpm dev                     # sample-api (:8787) + sample-web (:5173) together
pnpm docs:build              # documentation site generated from docs/ (apps/docs-site; nothing there is content — edit docs/*.md)
node cli/bin/kohaku.js conformance --self                                    # spec self-check
node cli/bin/kohaku.js conformance --rest http://localhost:8787/api/kohaku  # REST black-box check
node cli/bin/kohaku.js init --from <data.csv> --out <dir>   # Zero-Port quickstart project (the generated project resolves the published `^<CLI_VERSION>`, so a template change that depends on an unpublished API is a type error until 0.4.1 ships; pack-smoke verifies the tarballs, so CI does not show it)
node cli/bin/kohaku.js init --mcp --from <data.csv> --out <dir>   # same, plus a stdio + Streamable HTTP MCP front door and a Claude Desktop config
pnpm --filter @kohaku-ui/mcp-renderer run build       # tsc + the core-only single-file renderer build (dist/renderer.html)
pnpm --filter @kohaku-ui-sample/mcp build:renderer   # single-file build of the shared renderer for MCP
pnpm --filter @kohaku-ui-sample/mcp start:http       # MCP over Streamable HTTP for external chat (claude.ai/ChatGPT) (:8788, unauthenticated demo)
pnpm --filter @kohaku-ui/spec run generate-schemas   # regenerate spec/schemas after changing spec-core Zod (CI checks for drift)
node cli/bin/kohaku.js dataset export --fixations <fixations.json> [--golden <dir>] [--tenant <id>] --out <file.jsonl>  # distillation dataset (docs/user-guide.md)
KOHAKU_LLM_PROVIDER=claude pnpm --filter @kohaku-ui-sample/api run measure-grammar-latency  # calls a real LLM; excluded from `pnpm test` (docs/design.md#prompt-caching)
node scripts/release-notes.mjs 0.2.0    # preview the draft GitHub release body generated from the package CHANGELOGs
pnpm --filter @kohaku-ui-sample/playground run dev             # the static playground, server-free, replaying recorded LLM responses (docs/user-guide.md §10)
pnpm --filter @kohaku-ui-sample/playground run build           # strict mode: fails if any Node-only import is reachable from the browser bundle
pnpm vitest run --project playground-drift                     # replays whatever fixtures actually exist against a fresh host; not part of `pnpm test`
KOHAKU_LLM_PROVIDER=ollama KOHAKU_LLM_MODEL=gemma4:e4b pnpm --filter @kohaku-ui-sample/playground run record-fixtures  # calls a real LLM; never run in this repo yet (docs/user-guide.md §10)
```

**Python implementation (python/)**: a wire-compatible full port of the TS implementation (conformance CONFORMANT). Details: [python/README.md](python/README.md).

```bash
cd python && uv sync && uv run pytest && uv run mypy && uv run ruff check && uv run lint-imports  # full Python verification (lint-imports is the layer-direction contract check)
cd python && uv run python -m sales_api            # Python sample REST host (:8790; the default is a deterministic pseudo-LLM. Requires cd python)
cd python && uv run python -m sales_api.mcp_http   # Python MCP over Streamable HTTP (:8791; stdio is sales_api.mcp_main)
pnpm --filter @kohaku-ui/spec run generate-cross-language-fixtures  # regenerate cross-language canonical-JSON goldens (CI checks for drift)
pnpm --filter @kohaku-ui/registry run export-core-catalog           # re-export the core catalog JSON (CI checks for drift)
```

**Verification discipline**: after any change, always run `pnpm test && pnpm typecheck && pnpm check:ci`. **If you change a spec-core Zod schema, regenerate `spec/schemas` with `pnpm --filter @kohaku-ui/spec run generate-schemas` and commit it** (CI checks the diff between the regenerated output and `spec/schemas`). For a live check of the LLM path: `KOHAKU_LLM_PROVIDER=ollama KOHAKU_LLM_MODEL=gemma4:e4b pnpm dev` (local ollama, no key needed). Formatting and lint rules live in `biome.jsonc`; the rules that are deliberately off carry their measured violation count and the reason inline — extend that note rather than silently re-enabling one.

## Layout essentials

- **Packages export src directly during development** (`exports` points at `.ts`). tsx / Vite / Vitest resolve TS directly, and tests, typecheck and coverage never look at build output. Publishing does not change that: `publishConfig` (generated by `pnpm meta:sync`) overlays `exports` with `dist` only inside the tarball, and `pnpm build:dist` emits it with the same `tsc` the typecheck uses. Exception: only cli has `bin/kohaku.js` (a launcher via tsx); the published bin is `dist/index.js`.
- Dependency direction (no reverse flow): `spec-core → {registry, data-binding, storage-memory, storage-postgres, storage-redis, authz-hmac, port-contracts} → {intents, authz-jwt} → {composer, renderer-core, semantic-llm} → host-core → {sandbox, lineage, evals, host-rest, host-mcp-apps, client, otel} → {renderer-react, renderer-wc, admin-react} → host → mcp-renderer → apps`.
  - `admin-react` (`@kohaku-ui/admin-react`) is the governance console (Lineage / Analytics / Promotions / Fixations / Approvals) as embeddable React components. The Approvals tab is the approver's inbox for `"approve"`-tier Actions: `derivePendingApprovals` derives the pending list from the lineage tail (no server-side pending store, design.md #72) and Approve mints a bearer token via `POST /approvals`. It depends on `client` + `renderer-core` + `sandbox` + `spec-core` only, with React as a peer (never `renderer-react` / `host-rest`; `packages/admin-react/test/boundary.test.ts` pins the manifest and every `src` import against that list; `@kohaku-ui/lineage` is a devDependency used by tests alone, to pin the promotion-status vocabulary). Everything product-specific is injected: the `KohakuClient` (tenant / role headers), `AdminMessages` (EN default; sample-web passes JA), `ThemeTokens`, `promotionDefaults` (draft prefill + `queryTemplate.path` choices) and `toolbar` / `extraTabs` slots (plus `hiddenTabs` to leave a built-in tab out). sample-web's `AdminPage` is a thin wrapper.
  - **`composer` is the generation side of the Spec** (deps: spec-core + registry + llm): L0/L1/L2 generation, the repair loop, deterministic post-processing, and the Spec cache behind `compose()`/`ComposePolicy`. For L2 free generation, `ComposePolicy.designSystem` (`DesignSystemGuide`) is the model-facing design-system surface: `.kit` — the built-in `DEFAULT_KIT_VOCABULARY` is the class vocabulary presented to the model — enables the `L2_UNKNOWN_CLASS` lint, which sends invented classes outside that vocabulary back for repair (paired with renderer-core's `defaultDesignKit` CSS on the render side, below). The vocabulary is also exposed under the `@kohaku-ui/composer/design-system` subpath so a downstream package whose tsconfig sets `"types": []` (e.g. sandbox) can import it without pulling composer's full `index.ts` — and therefore `@kohaku-ui/llm`'s `process.env` usage — into its typecheck.
  - **`renderer-core` is the framework-free / DOM-free shared core** (deps: spec-core + registry〈types〉 + data-binding). The **single source of truth** for event governance, write-target resolution, the state store, BoundDataController, per-part presenters, UI messages, theme resolution, and the default design kit (`defaultDesignKit`: the CSS the sandbox injects for L2; its class vocabulary lives in composer). `renderer-react` (React) and `renderer-wc` (Web Components) import it and consume the same core (proof that "the declarative UI Spec is renderer-independent" = A2). renderer-core has no DOM lib (contamination is caught by typecheck).
  - **`host-core` is the framework-free shared host core** (deps: spec-core + data-binding + composer + registry + llm — registry was added for `catalog-impact.ts` / `catalog-migration.ts`'s catalog analysis, design.md #65, and llm for `errors.ts`'s `LlmError` classification, design.md #71). Consumed by `host-rest` and `host-mcp-apps` the same way `renderer-core` is consumed by the two renderers: a single source of truth for the fixation (L1→L0) delivery + staleness self-healing sequence (`composeWithFixation` / `resolveFixatedResult` / `settleFixation`, driven by a host-supplied `FixationDeliveryHost`), capability issuance (`issueCapabilityForSpec` for a composed Spec / `issueCapabilityForRefs` for a ref list, default TTL 600s, and the fail-closed `issueSpecCapabilitySafely` wrapper both hosts call) and its verify-side counterpart `verifyCapabilitySafely` (a fail-closed wrapper around `authz.verify`: a thrown verify becomes `{ kind: "unavailable" }`, which REST maps to 503 `INTERNAL` with `CAPABILITY_VERIFICATION_UNAVAILABLE_MESSAGE` and MCP maps to a structured tool error), read-ref parsing (`parseInvokableRef`: reserved-param split + merge, source check; verify and error mapping stay in each host), the fail-open Action manifest build (`buildActionManifestSafely`: a rejected `OperationIndex` or a throwing build is reported and the manifest is simply absent), the post-write effects response (`applyActionEffects`, fail-open), intent resolution (`resolveIntent`), the cancelled-aware fail-open composed-result recording (`recordComposedResult`, plus `recordComposedAndFallback`, the `recorder.composed` → fallback pair; these delivery helpers are order-neutral — each host keeps its own capability / manifest / record step order and its own `onError` endpoint names, and there is deliberately no single compose-delivery orchestrator), client-safe error messages (`errorMessage` / `clientMessageFor`, plus `classifyHostError`, which maps an `LlmError` PROVIDER / CONFIG / ABORTED to the fixed `LLM_PROVIDER_UNAVAILABLE_MESSAGE` — REST answers 503 `INTERNAL`, MCP a structured tool error — while `isTypedHostError` keeps its "any Error with a string `code` is typed" rule with `LlmError` as its single exclusion), and fail-open observability-hook helpers (`notifyHook` / `failOpen`). Both profiles wire the host object's `serialize` to a shared keyed mutex: REST keys it by `(tenant, intentHash)`; MCP keys it by `intentHash` alone and never resolves a tenant.
  - **`host`** (`@kohaku-ui/host`, design.md #52) is the one-call facade: `createKohakuHost()` wires the default Port implementations (`createMemoryStoragePort`, `createHmacAuthzPort`, `createLlmSemanticPort`, `resolveCatalog(coreCatalog)`) into `host-rest`'s `createKohakuRoutes`, with every default overridable and `host-core`'s `createConsoleErrorReporter` wired in for free. Depends on `host-rest` + `host-core` + `composer` + `semantic-llm` + `storage-memory` + `authz-hmac` + `registry` + `intents` + `lineage` + `llm`; depends on no renderer. MCP is a separate `@kohaku-ui/host/mcp` subpath (`attachKohakuMcp`) that `src/index.ts` never imports, so a REST-only consumer never needs `host-mcp-apps` or `@modelcontextprotocol/server` — both are optional peer dependencies of this package (not ordinary ones), installed only by a consumer that wants `./mcp`. `kohaku init` and `kohaku scaffold ports` both build on it.
  - **`mcp-renderer`** (`@kohaku-ui/mcp-renderer`, design.md #56) distributes the shared MCP Apps renderer (the code that runs inside the iframe an MCP host mounts) as its own package instead of leaving it embedded in `apps/sample-mcp`. `.` is a **dependency-free** `loadRendererHtml(): Promise<string>` that reads this package's own pre-built `dist/renderer.html` (core component set only, no product-specific implementations) — a REST-only or non-MCP consumer of the monorepo's packages never installs it, and even an MCP consumer that only wants the stock renderer installs nothing beyond this package. `./boot` (`bootMcpRenderer({ registerImpls?, root? })`) is the source the core build itself is built from, and also what a product rebuilds with its own component implementations baked in (mirroring the Web app's registry overlay, "Strategy A" pixel parity) — its `@kohaku-ui/renderer-react` / `renderer-core` / `data-binding` / `spec-core` / `@modelcontextprotocol/ext-apps` / `react` / `react-dom` dependencies are all **optional peerDependencies**, so `src/index.ts` never imports `./boot` and a plain `npm install @kohaku-ui/mcp-renderer` pulls in none of them. `apps/sample-mcp`'s own renderer (sales-domain implementations baked in) is now a thin rebuild against `./boot`; `kohaku init --mcp` wires a generated project onto the core-only `.` build with no rebuild step at all.
  - `renderer-wc` is a single `<kohaku-surface>` (Custom Elements + Shadow DOM). It **reuses `sandbox` (`mountSandbox`) by importing it directly**. Parity (semantic DOM equivalence React ⇄ WC + shared event behavior) is guaranteed by `packages/renderer-wc/test/parity` (renderer-react is a devDependency there).
  - `llm` is an independent leaf that does not depend on spec-core. It depends only on zod and ai-sdk; composer / evals / host-core use it. `host-a2ui` is an independent leaf depending only on spec-core (the A2UI-compatible profile skeleton). `client` is the typed host client SDK depending only on spec-core + data-binding, and **does not depend on host-rest** (host-rest is a devDependency only as a test counterpart). The wire-contract types for REST error codes, `HostErrorCode` / `ErrorEnvelope`, are defined in spec-core, not host-rest; host-rest re-exports them for backward compatibility.
  - `storage-memory` (`@kohaku-ui/storage-memory`), `authz-hmac` (`@kohaku-ui/authz-hmac`) and `port-contracts` (`@kohaku-ui/port-contracts`, **private, test-only**) are leaves on spec-core alone — a Port reference implementation must never pull composer / llm in through host-core, so the in-process keyed mutex they share with the hosts (`createKeyedMutex`) lives in spec-core (host-core re-exports it). `storage-memory` holds the two reference StoragePort implementations: `createMemoryStoragePort()` (pure in-process, the Zero-Port default and the test double) and `createFileStoragePort(dataDir)` (the former sample-api port: Spec cache in memory, lineage / promotions / fixations under `dataDir`). `createMemoryStoragePort` is also re-exported alone from the `./memory` subpath, which has no Node-only dependency (unlike `createFileStoragePort`, `node:fs`-based) — the browser-only static playground (`apps/playground`) imports from there instead of `"."`. `authz-hmac` is the HMAC-SHA256 capability token (`createHmacAuthzPort`). `port-contracts` exports `describeStoragePortContract` / `describeAuthzPortContract`; every StoragePort / AuthzPort adapter — including the production ones — must pass them. The contract itself stays `packages/spec-core/src/ports.ts`; these packages are reference implementations a product may replace.
  - `storage-redis` / `storage-postgres` / `authz-jwt` are **reference adapters** over `ports.ts` (deps: spec-core; `authz-jwt` also `authz-hmac`, to which it delegates capability tokens; drivers `ioredis` / `pg` are peers, `jose` a dependency). `storage-redis` and `storage-postgres` implement the whole StoragePort (Spec cache, lineage, promotion state, fixation, tenant scoping) so several host instances share one backend and serve the same Intent as `cache: "hit"`; `authz-jwt` resolves principal / roles / tenant from JWT / OIDC claims (shared secret or JWKS). Their backend-backed tests resolve a backend via `@kohaku-ui/port-contracts`'s `resolveAdapterBackend` (env URL → Docker/testcontainers → skip; `KOHAKU_ADAPTER_TESTS=require` forbids the skip in CI).
  - `otel` (`@kohaku-ui/otel`) is a thin, opt-in OpenTelemetry layer depending only on `composer` (peer: `@opentelemetry/api`) — unlike the other packages in its layer it does **not** depend on `host-core`. `createOtelComposeObserver` turns `ComposeObserver` calls into spans (`gen_ai.*` / `kohaku.*` attributes; restores `ComposeOptions.traceContext` as the span's parent so it nests under the caller's own trace) and is combined with a product's own observer via `composer`'s `composeObservers`. It ships no exporter/SDK wiring (that stays the host process's responsibility — see docs/user-guide.md's "Trace context / OTel" section); OpenTelemetry's GenAI semantic conventions are still "Development" status, so its attribute *key names* are independently overridable rather than documented as stable. `ComposeOptions.traceContext` (`{ traceparent; tracestate? }`, W3C Trace Context) is a purely additive field threaded through `ComposeTrace` / `ComposeErrorContext`; `host-core`'s `parseTraceContext` (shared by `host-rest`'s `traceparent` request header and `host-mcp-apps`' `_meta.traceparent`, MCP 2026-07-28 / SEP-414) validates the format before either host ever sets it.
  - `intents` is an environment-neutral independent leaf depending only on spec-core + data-binding (the Intent DSL). From `defineVocabulary` (a single source of value sets + labels) and `defineIntent` (a single Intent definition), it derives the SemanticPort `IntentDef`, GUI facet descriptors (`FacetView`), MCP tool inputs, and client coerce. sample-api uses it for the catalog definition (`intents/catalog.ts`); GUI facets are emitted by `pnpm intents:emit` (`apps/sample-api/scripts/generate-facet-views.ts`) into `apps/sample-web/src/generated/facet-views.json`, which sample-web imports as data (the web app has no dependency on server code / CI checks for drift).
  - `semantic-llm` (deps: spec-core + data-binding + intents + llm) is the default SemanticPort: `createLlmSemanticPort` maps a GUI action deterministically and an NL question via the LLM's structured output onto an `@kohaku-ui/intents` catalog (reference passing only — rows never enter the model's context), with product-specific rules and a fallback Intent as options. sample-api's `apps/sample-api/src/ports/semantic-port.ts` now builds on it, and `cli`'s `kohaku init` generates a project wired to it. The Intent layer stays a product responsibility — this package is a starting point, replaced the same way the other adoption-ladder defaults are (docs/user-guide.md §6). `semantic-llm` also owns the mutable `IntentCatalog` / `createIntentCatalog` (with a `revision` counter for add/remove), which sample-api's promotion flow uses through `apps/sample-api/src/intents/catalog.ts`'s `createSalesIntentCatalog`.
- **Port types (the framework boundary) are defined solely in `packages/spec-core/src/ports.ts` (a barrel over `src/ports/*.ts`, one file per Port)**: DomainPort / SemanticPort / AuthzPort / StoragePort (and the `CapabilityRevocationStore` extension consulted by revocation-aware AuthzPorts).
- The heart of the sample's wiring is `apps/sample-api/src/app-core.ts` (where all packages converge; `createApp` there takes a mandatory `repo` and has no Node-only import anywhere in its own graph). `app.ts` (the package's `"."` export) is a thin Node-facing wrapper around it — `repo` optional, defaulting to `domain/seed-fs.ts`'s disk read — and `./browser` (`browser.ts`) re-exports `app-core.ts`'s `createApp` directly; see that pair's own doc comments for why the split exists.
- `apps/playground` (`@kohaku-ui-sample/playground`) is a static, server-free build of sample-web's own `App` (unforked) that runs sample-api's `./browser` host entirely inside the browser tab via a same-origin fetch shim, a WebCrypto `AuthzPort` (`src/host/authz.ts` — `@kohaku-ui/authz-hmac` itself is Node-only), and a replay-only LLM (`@kohaku-ui/evals/replay`'s `ReplayLlm`) instead of a real model. `src/scenarios.ts` is the single list of demo scenarios the UI, the fixture recorder (`apps/playground/scripts/record-fixtures.ts`, written but never run — see docs/user-guide.md §10), the startup bootstrap, and the drift suite (`pnpm vitest run --project playground-drift`) all share.
- spec-core is environment-neutral (no DOM lib / @types/node dependency). Global APIs are used via structural typing on `globalThis` (see `canonical-json.ts`). Server-side packages set `"types": ["node"]` in tsconfig.

## Conventions

- ESM only (`"type": "module"`). TypeScript strict. Comments and error messages in English.
- **zod is a peerDependency in every package, pinned to a single version via the pnpm catalog** (`pnpm-workspace.yaml`). Bump the version only in the catalog.
- Adding a new package: run `pnpm install` at the root → vitest identifies it by the `name` in each package's `vitest.config.ts`. **A workspace directory without a vitest config makes the root config recurse into itself and fail**, so add a `passWithNoTests: true` vitest.config.ts even without tests (see apps/sample-mcp).
- Always run tests **from the repository root** (with cwd inside a package, only that package runs).
- Never write tests that call an LLM. Use FakeLlm from `@kohaku-ui/llm/fake` (scripted responses) or FixtureLlm from `@kohaku-ui/evals` (record/replay, filesystem-backed). `@kohaku-ui/evals` also has two Node-free subpaths: `./judge` (`createJudge` + `SchemaExtractor`, what a product's own app wiring should import instead of `"."` to avoid pulling in FixtureLlm's `node:fs`) and `./replay` (`ReplayLlm`, a replay-only LlmPort for a browser host with no filesystem, plus the `fixtureKeyOf`/`objectFixtureKey`/`textFixtureKey` key functions shared with FixtureLlm — a fixture recorded by one replays under the identical key via the other).

## Pitfalls (learned in the field)

- **Naming trap in `packages/llm/src/adapters/ai-sdk.ts`**: kohaku's own `LlmPort.generateObject` (unchanged, invariant contract) is unrelated to the Vercel AI SDK's own `generateObject`/`streamObject`, which AI SDK 7 deprecated in favour of `generateText`/`streamText` + `output: Output.object({schema})` (and renamed `system` to `instructions`). Don't reintroduce the SDK's deprecated calls when touching this file — the churn is meant to stay isolated here.
- **ollama / llama.cpp sporadically return 400 for structured output with large anyOf schemas, even for identical requests**. Countermeasure implemented: `KOHAKU_LLM_STRUCTURED_MODE=auto` (default) falls back automatically to prompt-JSON mode (`packages/llm/src/adapters/ai-sdk.ts`).
- **TypeScript 7's `stripInternal` matches the literal substring `@internal` anywhere in a JSDoc comment, not a structured tag at the start of a line**: a package built with `stripInternal: true` (every package's `tsconfig.build.json`) silently drops a declaration's `.d.ts` output if its comment merely *mentions* the marker in prose — e.g. a sentence explaining, in backticks, why the function is deliberately not given that marker still contains the triggering substring and gets stripped anyway. The runtime export still exists (`pnpm test` / `pnpm typecheck` never look at `dist`, so they notice nothing), but a re-export of that symbol from another file's `.d.ts` fails to resolve once packed — caught only by `pnpm smoke:pack`'s step 6 NodeNext type-check (`scripts/pack-smoke.mjs`). When a doc comment needs to talk *about* that marker (e.g. to explain why a function isn't tagged with it), split the word so the literal substring never appears, or say it without the `@`.
- With ollama, **use non-reasoning models** (gemma4:e4b etc.). Reasoning models (the qwen3.5 family) burn the token budget on thinking and L1 generation comes out empty.
- `apps/sample-api/.data/` is local runtime state (persistence for lineage / promotion / fixation; gitignored). **In tests, pass a mkdtemp temporary directory** (see `test/promotion.e2e.test.ts`). To reset the demo, deleting `.data` (with trash) is fine.
- Composer caching: L0/L1/L2 are all cached. `provenance.cache` is hit/miss/bypass/fixated. The cache is the substance of the identical-display guarantee; temperature 0 is auxiliary (write tests with this assumption).
- renderer-react tests require `globals: true` (@testing-library/react's auto-cleanup depends on the afterEach global).
- **A dynamic `import(expr)` with a variable specifier hides an optional Node-only dependency from a bundler (`@kohaku-ui/sandbox/smoke`'s `loadJsdom`/`loadVm` use this on purpose), but only works reliably for a real npm package resolvable via `node_modules` — not for this repository's own TypeScript source** (which is imported with a `.js` extension pointing at a `.ts` file, resolved by Vite/tsx's own tooling, not Node's native loader). Vite/Vitest's SSR module runner only rewrites a `.js`-suffixed relative specifier to the on-disk `.ts` file when it can see the specifier *statically*; a variable specifier defeats that the same way it defeats a bundler's dependency-graph analysis, so `import(moduleName)` fails at test time with "Cannot find module .../foo.js" for a local file, even though the exact same pattern works fine for `jsdom`. If you need to keep an optional Node-only default out of a browser-reachable file's own static import graph, split it into a separate wrapper module that the Node-only caller imports directly instead (see `apps/sample-api/src/app.ts` vs `app-core.ts`).

The documentation site (`apps/docs-site`, VitePress) is generated from `docs/`, `spec/SPEC*.md` and `python/README*.md` at build time into a gitignored `.generated/` directory; never commit anything under it and never edit generated files. Adding a page under `docs/` requires a sidebar entry in `apps/docs-site/src/sidebar.ts` (`test/sidebar.test.ts` fails otherwise). Relative links between documents keep working on GitHub and on the site as long as they point at files under those roots; a link to any other repository file is rewritten to its GitHub URL. Heading anchors follow GitHub's own slug rules (`apps/docs-site/src/github-slug.ts` makes VitePress produce the same ids), and `test/github-slug.test.ts` walks every mirrored page and fails if an anchored link does not resolve — so an in-repo `#anchor` link is checked, not just trusted.
