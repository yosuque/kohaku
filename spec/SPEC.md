# Kohaku Protocol Specification v0.1 (Draft)

English | [日本語](SPEC.ja.md)

An open specification for driving application-independent, general-purpose presentation components equally from GUI interaction and from natural language. For a design walkthrough of the implemented system, see [docs/design.md](../docs/design.md). The **[Normative]** / **[Draft]** / **[Reserved]** markers at the end of each section denote status.

The requirement keywords MUST / SHOULD / MAY follow RFC 2119. The machine-readable requirement list is in [conformance/manifest.ts](conformance/manifest.ts); the reference implementation is this repository's `packages/*`.

---

## 1. Overview and terminology [Normative]

| Term | Definition |
|---|---|
| **UI Spec** | Declarative JSON describing the structure and semantics of UI. Data, not code |
| **Surface** | A host that accepts input and renders (web / chat / mcp-app / …) |
| **Intent (normalized Intent)** | Natural language and GUI interactions normalized into a single representation. The source of the cache key. Its wire name is `CanonicalIntent` (§6.1) |
| **Intent catalog** | The set of registered Intent definitions (canonical name, param schema, query mapping) an application declares — distinct from the **Catalog** below (a set of UI *components*). The reference implementation's `IntentCatalog` (`apps/sample-api/src/intents/catalog.ts`) |
| **Catalog** | A set of typed UI components (ComponentDefinition). Merged in a federated manner (§3) |
| **Binding** | Pass-by-reference data resolution via `query://` URIs |
| **Lineage** | Audit records of Views (why this screen appeared) and Components (component provenance) |
| **Promotion / Fixation** | L2→L1 (registering a component into the catalog) / L1→L0 (fixing the structure of a frequent Intent) |
| **Surface capabilities** | The `supports: { type: semverRange }` a surface declares — which component types/versions it can render (§3.2, "Surface capability negotiation"). Unrelated to the bearer token below despite the shared name |
| **Capability token** | The bearer token issued per Spec that scopes on-behalf-of read/write authority over that Spec's `data.$ref`s and declared `action.invoke` names (§5) |

Architecture principle: **complete separation of Composition and Rendering.** Identical presentation for requests of identical content is guaranteed structurally by a single Composition Service and a Spec cache (key = intentHash + dataVersion + catalogFingerprint + optional generatorVersion (MAY)). generatorVersion is an optional component that separates generated artifacts by generation across prompt revisions and model changes; it becomes the trailing component of the key only when specified (identical to the legacy key when omitted).

**Protocol version strategy**: the host emits the current version `0.2` (the `kohaku` field of newly composed Specs). The accepted versions are `{0.1, 0.2}`, and existing `0.1` Specs (fixated pinnedSpec, etc.) remain valid and continue to be served (MUST). Features introduced in `0.2` (`state` / `visibleWhen` / `emit: "state.set"` / `data.bind` — [Draft]) are permitted only in Specs that declare `0.2` and MUST NOT appear in `0.1` (MUST NOT; the reference implementation rejects them with `VERSION_FEATURE_MISMATCH`). Because the version component of the cache key uses the emitted version, keys for newly composed Specs update exactly once at the `0.2` cutover (serving of existing fixations is unchanged).

## 2. UI Spec format [Normative]

Canonical example: [examples/quarterly-sales.spec.json](examples/quarterly-sales.spec.json). JSON Schema: [schemas/ui-spec.schema.json](schemas/ui-spec.schema.json).

### 2.1 Envelope

```json
{ "kohaku": "0.2", "intent": {…}, "dataVersion": "…", "state": {…}?, "components": […], "events": […], "provenance": {…} }
```

- **SPEC-ENV-001** The envelope MUST carry a `kohaku` version string (MUST). The value is one of the accepted-version set `{0.1, 0.2}` (see the version strategy in §1).
- `state` (MAY, kohaku >= 0.2, [Draft]) is the initial-value map for client-local state (`stateKey` → JSON value). It is confined to the Renderer and MUST NOT be sent to the server (MUST NOT). `stateKey` is `^[a-zA-Z][a-zA-Z0-9_]{0,63}$`.
- **SPEC-ENV-002** `intent.hash` MUST be of the form `sha256:<hex64>`, the hash of the key-deep-sorted JSON (canonical JSON) of `{canonical, params}` (MUST).
- **SPEC-ENV-003** A Spec MUST NOT contain theme information (MUST NOT). Tokens are resolved on the Renderer side.
- `provenance` carries `tier` (L0|L1|L2), `composedBy`, and `cache` (hit|miss|bypass|fixated) (MUST). `model` / `fallback` / `composedAt` are MAY. `fallback`, in addition to `{from, reason}`, MAY carry `kind` (`generation` = a deterministic fallback when L1/L2 generation is exhausted / `negotiation` = a capability-negotiation downgrade). If both occur, `negotiation` is recorded under last-writer-wins (a single Spec carries a single downgrade trace). `composedAt`, when present, MUST be ISO 8601 UTC with seconds precision (`YYYY-MM-DDTHH:mm:ssZ`; a fractional-seconds suffix is also accepted, but the `Z` designator and second-level fields are required — no bare offset or date-only form) (MUST). `generatorVersion` and `kit` (`{id, version}`) are also MAY. `generatorVersion` records the host's generator identity in effect at composition time; `kit` records the design kit's identity and version that the generated markup was written against. **SPEC-KIT-001** A surface that injects a design kit stylesheet SHOULD compare its own kit identity against `provenance.kit` and signal a mismatch rather than rendering unstyled markup silently (SHOULD).

### 2.2 Component model

- **SPEC-CMP-001** `components` is a flat list with unique `id`s (MUST). A node with `id: "root"` MUST exist (MUST).
- **SPEC-CMP-002** `children` is an array of ID references forming a DAG rooted at root, and MUST NOT contain cycles (MUST).
- A node SHOULD carry `version` (the resolved catalog semver) (SHOULD).
- An L2 node is expressed as `type: "sandbox.html"` + `artifact { inline | uri, sha256 }`. `sha256` MUST be verified before execution (MUST).
- `visibleWhen` (MAY, kohaku >= 0.2, [Draft]): a display-condition predicate. A backward-compatible union of **leaf** and **compound**. When false, the Renderer does not render that node together with its subtree (unmount).
  - leaf: `{ ref: "$state.<key>", <comparison> }`. The comparison is **exactly one** of `eq` / `ne` / `in` / `gt` / `lt` / `gte` / `lte` / `exists`. `eq`/`ne`/`in` use canonical equality of JSON values, `gt`/`lt`/`gte`/`lte` are numeric comparisons (false if the state value is non-number), and `exists` is the truth of whether the state value is other than null/undefined (`true` = present / `false` = absent).
  - compound: `{ all: [predicate…] }` (conjunction) / `{ any: [predicate…] }` (disjunction) / `{ not: predicate }` (negation). Recursion and nesting are allowed. Nesting depth is capped at 8 and the element count of `all`/`any` at 16; exceeding these is a validation error (MUST).
  - Every leaf `ref` reference key in the predicate tree MUST have an initial value in `spec.state` (MUST — guaranteeing determinism of initial rendering. `STATE_REF_UNKNOWN`).
- State-related structural validation error codes (kohaku >= 0.2): `STATE_REF_UNKNOWN` (missing initial value for a visibleWhen.ref) / `STATE_SET_INVALID` (the payload.key of state.set is not a static key, or is undeclared) / `VERSION_FEATURE_MISMATCH` (`0.1` contains a state feature). All are errors.

### 2.3 Data binding (pass-by-reference)

- **SPEC-DATA-001** Bulk data (rows, aggregate values) MUST NOT be embedded in a Spec (MUST NOT). Data is expressed only by the `data.$ref` reference `query://<source>/<path>?<params>`.
- The canonical form of a reference URI sorts query parameter keys in ascending order (MUST).
- A data response uses the tabular envelope `{ columns: [{key,label?,type}], rows: [...], dataVersion, total? }` (SHOULD). A `dataVersion` mismatch lets the client treat the data as stale.
- **SPEC-DATA-002** A Spec that has multiple `$ref`s with divergent versions SHOULD include `refVersions` (`$ref` URI → the `dataVersion` of that reference alone) (SHOULD). If `refVersions` is present, the Renderer MUST reconcile on a per-reference version basis (MUST. `refVersions?.[ref] ?? dataVersion`). The composite version `dataVersion: "multi:<hash>"` is a cache-key component and never matches an individual response version, so it cannot be used for reconciliation.
- **Server-side paging/sort [Draft]**: query parameters beginning with `_` form a **reserved namespace** used for the wire representation of paging/sort (`_cursor` / `_limit` / `_sort` / `_dir`). A Spec's `$ref` itself MUST NOT contain reserved parameters (MUST NOT — the client's `resolve(ref, {page, sort})` appends them). A data response MAY return an opaque cursor `nextCursor` when more data follows (MAY; the client passes it verbatim as the next request's `_cursor` without interpreting its contents). Reserved parameters are excluded from capability validation (see §5) — validation is an **exact match** against the base ref (= the canonical form of the `$ref` the Spec declared) with reserved parameters removed. A host SHOULD reject `_` parameters other than the known reserved keys (`_cursor` / `_limit` / `_sort` / `_dir`) (SHOULD — so that the data range cannot be altered by unauthorized parameters).
- **Bidirectional binding `data.bind` [Draft] (kohaku >= 0.2, A1)**: alongside `$ref`, `data` MAY carry `bind: { <param>: { $state: "<key>", values: string[] } }` (MAY). It injects the value of client-local state `$state` into the corresponding query parameter of `$ref` and re-resolves within the client — without a compose (server round-trip / LLM) — for cross-filtering and linked dashboards. `$ref` is the **concrete canonical URI of the initial variant with the bound parameters filled by the initial `$state` values**, so in the initial state the effective ref = `$ref`. `values` is the **static enumeration** of the bound value domain (v1 supports only discrete cases such as select; free input and continuous values are out of scope), and this is the single source of truth for capability enumeration (§5). Structural validation error codes (kohaku >= 0.2, all errors): `BIND_STATE_UNKNOWN` (the initial value of `bind.<param>.$state` is not in `spec.state`) / `BIND_PARAM_MISSING` (the bound parameter is not in the query of `$ref`) / `BIND_VALUE_INVALID` (the corresponding value in `$ref` is not in `values`, or does not match `String(spec.state[key])` — the three-way agreement of initial ref = initial state = authorized value) / `BIND_PARAM_RESERVED` (the bound parameter begins with `_`) / `BIND_VARIANT_LIMIT` (the total number of variants exceeds the cap of 256) / `VERSION_FEATURE_MISMATCH` (`0.1` contains bind).

### 2.4 Event model

- **SPEC-EVT-001** `events[].on` is of the form `<componentId>.<eventName>`, and the target ID MUST exist (MUST).
- `emit` is one of `intent.patch` | `intent.replace` | `action.invoke` | `state.set`.
- The `"$row.<key>"` / `"$value"` in a payload template are resolved by the rendering side with runtime values.
- **SPEC-EVT-002** The Renderer MUST NOT forward upstream any event not declared in the Spec (MUST NOT).
- `state.set` (MAY, kohaku >= 0.2, [Draft]): a write to client-local state. The payload carries a static `key` (a key already declared in `spec.state`) and the value to set `value` (templates allowed). It is self-contained within the Renderer and MUST NOT be sent to the server (MUST NOT — preserving the control of SPEC-EVT-002).

### 2.5 SpecPatch (incremental update)

The response of the interaction loop (recomposition from GUI interaction / events) can be expressed as the **semantic diff** from the previous Spec as a `SpecPatch` (an optimization over full retransmission; component-granular rather than JSON Patch).

- A patch consists of `components` `upsert` (replace on ID match, add if absent) / `remove` (delete by ID), plus replacement of `events` / `intent` / `dataVersion` / `refVersions`. `refVersions` is fully replaced, and `null` denotes deletion (the next Spec has no `refVersions`). An optional `kohaku` carries a protocol version change (present only when `prev.kohaku` differs from `next.kohaku`, e.g. a 0.1 Spec promoted to 0.2 by a patch that also introduces `state`); when absent, `applyPatch` keeps the target Spec's version.
- The canonical order is `orderComponents` (DFS from root). The result of applying a patch MUST equal a Spec fully composed for the same Intent (including deterministic post-processing).
- **SPEC-PATCH-001** Applying the patch obtained from `diffSpec(prev, next)` to `applyPatch(prev, …)` MUST yield a result equal to `next` (round-trip, MUST). Reference implementation: [packages/spec-core](../packages/spec-core).

## 3. Component Catalog

### 3.1 ComponentDefinition [Normative]

`{ type, version(semver), description, propsSchema(JSON Schema), capabilities { events, data: none|optional|required, children, editable? }, implementation { kind: native | sandbox-template }, fallback?, golden?, deprecated? }`

- props MUST be JSON-representable (MUST. Dates and the like are expressed as strings).
- `description` is transcribed into the generation prompt as selection guidance for the LLM (SHOULD be concrete).
- **Type-naming convention**: a core type's `type` uses `<namespace>.<name>` (e.g. `layout.stack`, `control.select`). The `present*` family (`presentList`, `presentMetric`, `presentChart`, `presentForm`, `presentSpreadsheet`, `presentMarkdown`) is a deliberate exception: it keeps the flat camelCase name it was given when v0.1 fixed the wire contract — renaming it now would change the wire contract and the catalog fingerprint (a breaking change, not a naming cleanup). New core types and product extensions SHOULD use a namespaced name.
- **`deprecated?`** (MAY) marks a part as superseded: `{ reason, since?, replacedBy?: { type, version? }, sunset? }`. A deprecated part MUST continue to validate Specs that already reference it (MUST — deprecating a part changes what gets generated from here on, not what already renders) but SHOULD be excluded from the L1 generation vocabulary (SHOULD; §4). When `replacedBy` is present, it MUST resolve to another entry of the same resolved catalog — matching `type`, and matching `version` exactly when `version` is given (MUST). A host MAY expose this field on `GET /catalog` (§6.1); when the part is not deprecated the field is omitted rather than sent as an explicit absent value.

The reference implementation additionally supports a TS-only, non-wire `migrateProps(props)` hook next to `fallback` for rewriting a deprecated part's props into its `replacedBy`'s shape; being a function, it is never serialized and carries no normative wire meaning (see design.md #65).

### 3.2 Surface capability negotiation and fallback [Draft]

A surface declares `supports: { type: semverRange }`. Unsupported components are downgraded through the definition-side `fallback` chain, whose terminal is `presentMarkdown` (a text fallback) (MUST). The downgrade is recorded in `provenance.fallback`.

### 3.3 Federated distribution [Draft]

Catalog = core ⊕ product contributions ⊕ promotions. Overriding an existing type is allowed only on a semver increase (MUST). The catalog fingerprint (the hash of the sorted join of `type@version`, with sandbox-template entries appending `#fnv1a64(html)` and, for an entry carrying `deprecated`, further appending `!deprecated`) is a cache-key component. Marking a part deprecated therefore changes the fingerprint (and so the compose cache key) for that catalog, while leaving every other entry's identity string — and so its contribution to the fingerprint — unchanged.

## 4. Composition rules [Normative (post-processing norms are Draft)]

- **L0 (fixed)**: deterministic generation from templates/fixation. Does not go through the LLM.
- **L1 (declarative composition)**: the LLM's job is limited to "selection from the catalog + filling typed props" (MUST). The envelope (intent / dataVersion / provenance) MUST NOT be generated by the LLM (MUST NOT). **CMP-GEN-001** `data.$ref` MUST be constrained to the resolved QueryHandle set (MUST), either at the schema stage (the enumeration (enum) presented to the generator — the default) or, when the implementation opts for an intent-independent generation grammar instead, via explicit post-generation validation.
- **L2 (free generation)**: a sandbox-only escape hatch. Generated code MUST NOT have any data path other than the bridge API (`window.kohaku`), and MUST NOT be able to navigate the sandbox document, open windows, or issue network requests: the host MUST execute it in a context that exposes no `document`, no assignable `location`, and no `window.open` (SBX-EXEC-001).
- **CMP-DET-001** For the same intentHash + dataVersion + catalogFingerprint, the host MUST return the same components / events (MUST. Guaranteed by the cache).
- **CMP-DET-002** A cache entry reachable only through L2 (free generation) MUST NOT be returned to a session whose effective policy disallows L2 (MUST NOT). Guaranteed by folding the policy's L2-availability (`allowL2` / route-tier) into the cache-key fingerprint, so a session with L2 disallowed can never hit a cache entry populated under a policy that allowed it — the reverse direction (a session that allows L2 hitting a cache entry produced while it was disallowed) is likewise excluded by the same mechanism.
- Deterministic post-processing (ID normalization, chart-type rules, order normalization, props normalization) is always applied to LLM output (SHOULD).

## 5. Security [Normative]

- **SBX-ATTR-001** The sandbox attribute of the L2 iframe MUST NOT include `allow-same-origin` (MUST NOT).
- **SBX-CSP-001** The CSP of the L2 document MUST include `connect-src 'none'` and MUST block network I/O (MUST). A host MUST NOT allow any fetch directive (`img-src` / `font-src` / `media-src` / `script-src` / `style-src` / `worker-src` / `child-src` / `manifest-src`, and their `-elem`/`-attr` variants) to name an external origin — only `'none'`, `data:`, `blob:`, and inline keyword sources (`'unsafe-inline'` / `'unsafe-eval'` / `'unsafe-hashes'` / `nonce-*` / `sha256-*` family) are acceptable (MUST NOT).
- **SBX-EXEC-001** Generated script MUST run in a dedicated Worker that exposes no `document`, no assignable `location`, `window.open`, `importScripts`, or network access (MUST). DOM effects MUST be applied only through the host runtime's mutation protocol, and the applier MUST reject any element, attribute, or style property outside its allowlist (MUST).
- **SBX-NAV-001** A navigation of the sandbox document (the guest document being replaced, e.g. via `location` assignment, `window.open`, `<meta http-equiv=refresh>`, or a followed link) MUST be treated as a fault: the host MUST tear the iframe down and MUST NOT let the guest continue running in the replaced document (MUST). Since SBX-EXEC-001 already denies the guest a `document`, an assignable `location`, and `window.open` of its own, this is defense in depth against an exec-isolation failure rather than the primary control.
- **SBX-BRG-001** The bridge resolves only references that exactly match the `data.$ref` of the corresponding node in the Spec (MUST). Violations are rejected with `-32001`. Quota exceedance (per-minute counts and concurrency of fetch / event / telemetry / resize, and response/payload size) is `-32002`, response oversize is `-32003`, and resolution timeout is `-32004`.
- The capability token represents on-behalf-of delegation of authority and is issued with a read scope covering the set of `$ref`s within the Spec (MUST). The token MUST NOT be passed inside the L2 iframe (MUST NOT) — the parent-side bridge acts as proxy.
- **Write-scope restriction to DomainPort operations**: a write scope (issued for a declared `action.invoke` action name) SHOULD be limited to the operations `DomainPort.listOperations()` enumerates (SHOULD). An action name not among them SHOULD be dropped from the issued capability rather than granted (SHOULD — a hallucinated or injected `action.invoke` action name from L1/L2 generation MUST NOT become a bearer write scope). The host SHOULD report each dropped action via its failure-path observability hook (§4's `onError`-equivalent); dropping a scope MUST NOT fail the capability issuance itself (fail-open — the capability is still issued without that scope).
- **Governed Actions [Draft]** (design.md #62/#63): a `DomainPort` operation MAY declare `tier` (`"auto"` (default) / `"confirm"` / `"approve"`) and `paramsSchema` (kohaku's own closed JSON Schema subset — §2.3's forgery-proofing principle extended to write payloads, not a general-purpose schema language: `type`, `properties`, `required`, `additionalProperties: false`, `enum`, `minimum`/`maximum`, `minLength`/`maxLength`, `items`, `maxItems`, `x-message`, and **no** `pattern`, which would reintroduce ReDoS risk and a JS/Python regex-dialect mismatch). When it does, the following apply to every write surface (REST's `POST /binding/action`, §6.1; MCP's `${prefix}_action`, §6.2) equally:
  - **ACT-PRM-001** A payload for an action with a declared `paramsSchema` MUST be validated against it, and rejected (`422 ACTION_PARAMS_INVALID` / the MCP structured-error equivalent, §6.1/§6.2) **before `DomainPort.invoke` ever runs** (MUST). Validation runs before the tier check below, so an already-invalid payload never additionally demands a confirmation or an approval for it.
  - **ACT-APR-001** An `"approve"`-tier action MUST NOT be invoked without a token that (a) is bound to the exact `(action, payloadHash, requesterId, tenant)` of this invocation, (b) has not expired, (c) has not already been consumed, when the host configures single-use enforcement, and (d) was issued by a principal other than the requester (an implementation MUST refuse to issue a self-approval in the first place) (MUST — a violation of any of (a)–(d) is `403 APPROVAL_REQUIRED` / the MCP equivalent). A verification failure the host cannot itself classify as allow/deny (e.g. an approval-store outage) MUST be treated as a denial (fail-closed).
  - **ACT-CNF-001** A `"confirm"`-tier action SHOULD NOT be invoked without the same-request body explicitly carrying `confirmed: true` (SHOULD — a request omitting it SHOULD receive `403 APPROVAL_REQUIRED` / the MCP equivalent, naming tier `"confirm"`). SHOULD rather than MUST: unlike `"approve"` (a genuine authorization boundary between two distinct principals), `"confirm"` is a misclick-prevention safety net the same principal satisfies unilaterally, so a host MAY additionally accept an equivalent product-specific same-request confirmation signal instead of the literal field name.
  - **LIN-ACT-001** A host that records governed-Action outcomes to its audit log SHOULD do so under a distinct `action.*` event family (`action.invoked` / `action.denied` / `action.approvalRequested` / `action.approved`), each carrying the action name and `payloadHash` but never the payload's own field values, so approval-adjacent audit trails never become a second copy of write content (SHOULD).
- **Capability validation of reserved parameters [Draft]**: `/binding/resolve` splits the received ref into base (the canonical form with reserved parameters beginning with `_` removed) and reserved, and **performs capability validation against the base** (MUST). Because the base matches the original `$ref`, it is covered by the issued read scope (§2.3). Reserved parameters are merged with the base parameters and passed to the DomainPort (the `_` namespace convention — the DomainPort signature is unchanged). It MUST NOT be possible to bypass the capability scope via reserved parameters (MUST NOT — validation is always base-relative).
- **Variant-enumeration capability for bidirectional binding [Draft] (A1)**: for components carrying `data.bind` (§2.3), the host MUST enumerate at compose time every effective ref reachable through the Cartesian product of `values` and **MUST issue each variant with a read scope** (MUST. Including the initial variant = `$ref`). Rationale: the reserved parameters `_` could be excluded from validation because "reorder / slice" **does not change which data is authorized**, but bind's bound parameters **filter = change which data is returned**. Therefore the reserved-namespace exclusion model cannot be reused (excluding them would let the client slip past base authorization with an arbitrary filter value); instead, the finite set of reachable refs is fixed at compose time and all of them are authorized. Because the client can build an effective ref only from a value chosen from `values` (= the authorized set), the reachable-ref set matches the compose-time authorized set (the no-forgery principle). Values outside `values` are not in the capability and are rejected (MUST). A cap (256) is placed on the total number of variants, and the capability of a Spec that exceeds it MUST NOT be issued (MUST NOT. `BIND_VARIANT_LIMIT`).
- Audit-log mandatory items: view.composed (specHash / intentHash / tier / cache / surface), component.generated / used, component.reviewed (approver), component.published, intent.fixated.
- **LIN-PRM-001** A human `component.reviewed(approve)` MUST exist before `component.published` (MUST). Automatic approval is not permitted in v0.1.

## 6. Transport profiles

### 6.1 REST profile [Normative]

Under the base path, the following are exposed (reference implementation: `@kohaku-ui/host-rest`):

| Route | Requirement |
|---|---|
| `POST /compose` | `{intent}` or `{input}` → `{spec, capability, actions?}`. **REST-CMP-001** the spec conforms to §2 (MUST). **REST-CMP-002** re-requesting the same intent is a cache hit with identical components (MUST). **REST-ERR-001** an invalid body (non-JSON, or both `input` and `intent` missing) is 400 with the error envelope below (MUST). `actions?` is described below [Draft] |
| `POST /intent/normalize` | **REST-INT-001** `{input}` → `{intent, source}` (MUST) |
| `POST /events` | **REST-EVT-001** `{intent, event{on, payload}}` → `{spec, capability, actions?}` (MUST) |
| `GET /binding/resolve?ref=` | **REST-BND-001** no capability is 401 (MUST). **REST-BND-002** with a valid capability, returns the tabular envelope and dataVersion matches the per-reference expected version (`refVersions?.[ref] ?? dataVersion`, §2.3) (MUST) |
| `POST /binding/action` | performs a write with a write-scope capability (MUST covers authorization only). **REST-BND-003** no capability is 401; a valid capability that lacks the needed write scope (e.g. a read-only capability) is 403 (MUST). The response is `{result, invalidates?, refVersions?}` (SHOULD). `invalidates` is the exact-match set of stale `query://` URIs, `refVersions` the per-reference new versions (§2.3). A host that does not support this returns only `{result}` (backward compatible). **Governed Actions [Draft]** (§5's ACT-PRM-001/ACT-APR-001/ACT-CNF-001, design.md #62/#63): when the invoked action is a `DomainPort` operation with a declared `paramsSchema` and/or `tier`, the payload is validated and the tier enforced before the write runs — 422 `ACTION_PARAMS_INVALID` on invalid params, 403 `APPROVAL_REQUIRED` when a `"confirm"`-tier request omits `confirmed: true` or an `"approve"`-tier request's `approval` token is missing/invalid. The request body accordingly gains optional `confirmed` / `approval` fields |
| `POST /approvals` | **[Draft]** (design.md #63) an authorized approver (governance kind `action.approve`) mints a token for someone else's pending `"approve"`-tier action: `{action, payloadHash, requesterId, ttlSeconds?}` → `{approval}`. Rejects a self-approval (`requesterId` equal to the caller) with 400 |
| `GET /catalog` | **REST-CAT-001** the serialized list of ComponentDefinitions + catalogVersion (MUST) |
| `GET /lineage` `POST /telemetry` `GET/POST /promotions…` `GET/POST /fixations…` | the control plane (SHOULD). **REST-ERR-002** `/promotions` and `/fixations` GETs are either 200 with their documented shape or a 501 `NOT_IMPLEMENTED` envelope. **REST-LIN-001** `/lineage` has an `{events:[]}` shape and respects `?limit=`. **REST-GOV-001** `/promotions/:id/actions` is 400 for an invalid payload and 404 for a valid action on an unknown artifact. **LIN-PRM-001** (§5) is also checked against `/lineage` |

Error envelope: `{ error: { code, message } }`. `code` is one of BAD_REQUEST / INTENT_INVALID / CAPABILITY_REQUIRED / CAPABILITY_DENIED / REF_NOT_FOUND / SOURCE_MISMATCH / NOT_FOUND / PROMOTION_INVALID / PROMOTION_NOT_PUBLISHED / COMPOSE_FAILED / INTERNAL / NOT_IMPLEMENTED / RATE_LIMITED / ACTION_PARAMS_INVALID / APPROVAL_REQUIRED. `ACTION_PARAMS_INVALID` (422; Governed Actions [Draft], design.md #62) additionally carries `error.issues: {path, code, message}[]` (the exact array `validateActionParams` returned). `APPROVAL_REQUIRED` (403; design.md #63) additionally carries `error.approval: {requestId, action, tier, payloadHash}`. **REST-ERR-001** `POST /compose` MUST reject a non-JSON body and a body missing both `input` and `intent` with HTTP 400 and this envelope (MUST). The named routes of the control system (promotions) use NOT_FOUND (404: artifact absent) / PROMOTION_INVALID (422: transition rejected) / PROMOTION_NOT_PUBLISHED (409: approval has not reached publish, carrying the state that stopped at `error.status` — the promotion state, **distinct from the HTTP status code of the response itself**). SSE streaming (`POST /compose/stream`) is described in §6.1.1 [Draft].

**Rate limiting [Draft]**: a host MAY enforce a rate limit on the compose-family routes (`/compose`, `/events`, `/binding/action`) (MAY) — the reference implementation's per-tenant/per-principal declarative policy is documented in `docs/user-guide.md`'s budget/rate-limit section. **REST-RL-001**: when a host enforces such a limit and a request exceeds it, the response MUST be HTTP 429 with the error envelope's `code: RATE_LIMITED` (MUST), and the host SHOULD additionally set the HTTP `Retry-After` header, in seconds (SHOULD); the envelope's `error.retryAfterMs` MAY carry the same backoff in milliseconds for a caller without access to response headers (MAY). Governance/control-plane routes (lineage / promotions / fixations) are not subject to this limit. Because enforcing a rate limit at all is optional (MAY) and only exercised when the reference host is configured with a rate-limit policy, [conformance/manifest.ts](conformance/manifest.ts) registers this as **REST-RL-001** with `level: "SHOULD"` and `verification: "reference"` — guaranteed by the reference implementation's package tests — rather than a black-box check against the conformance CLI's unconfigured demo host.

**Governed Actions manifest [Draft]** (design.md #62/#63/#64, ACT-PRM-001/ACT-APR-001's `actions?` companion): the response of `POST /compose`, `POST /events`, and the `event: spec` payload of `POST /compose/stream` (§6.1.1) MAY additionally carry `actions`, a map from action name to `{tier, paramsSchema?, confirmMessage?}` for each write action (`emit: "action.invoke"`) the Spec declares that the host also recognizes as a `DomainPort` operation (`listOperations()`). `tier` is one of `"auto"` (the default, equivalent to omitting it) / `"confirm"` / `"approve"`, `paramsSchema` (when present) is the same value the operation's `OperationDescriptor.paramsSchema` declared, and `confirmMessage` (when present) is a human-readable prompt for a `"confirm"`-tier gate. `actions` is placed **outside the Spec itself**, alongside `capability` — it MUST NOT affect `specHash` or the cache key (MUST NOT), and its absence (a Spec with no write actions, or a host that has not implemented governed Actions at all) leaves the response byte-identical to before this field existed. `POST /binding/action` enforces `tier` and the named `paramsSchema` before invoking the write (422 `ACTION_PARAMS_INVALID` / 403 `APPROVAL_REQUIRED`, added to the error-code list below), and `POST /approvals` issues the bound grant an `"approve"`-tier action requires, authorized as a control-plane route (governance kind `action.approve`).

When the response spec of `/compose` / `/events` contains `provenance.fallback` (a deterministic downgrade from L1/L2 generation failure, or a component downgrade from capability negotiation), `view.fallback` is recorded in lineage (SHOULD). The payload is specHash / reason / surface / kind (`generation` | `negotiation`) / intentHash. The source of the decision is the response spec rather than the trace, so as not to miss a negotiate downgrade that can occur at finish on every request even after a cache hit.

**Intent validation for directly-specified Intents [Draft]**: `SemanticPort` may optionally implement `validateIntent` (spec-core's `ports.ts`) to validate and normalize an Intent the caller specifies directly (`kind: "intent"`) rather than deriving it from NL/GUI input — the path `POST /compose`'s `{intent}` body, `POST /events`' `intent` (the pre-event `current`), and the fixation-approval endpoint (`/fixations/approve`) all funnel through. **REST-INT-002** when the host's `SemanticPort` implements `validateIntent`, an unknown canonical or invalid params SHOULD be rejected with 422 `INTENT_INVALID`, leaving no trace in the cache, lineage, or fixation store (SHOULD). A host whose `SemanticPort` does not implement `validateIntent` keeps the historical behavior of finalizing the caller-supplied Intent unchecked (backward compatible).

**Multitenancy [Draft]**: a host MAY isolate the control plane (lineage / promotion aggregation / fixation) per tenant via `SessionContext.tenant` (resolved from the request by the product; the reference implementation is `KohakuHostDeps.tenant(c)`) (MAY). The aggregation scope of the control-system routes (promotions / fixations) uses the session-derived tenant and is not received via query parameter. **`query://` is tenant-neutral and the cache key MUST NOT include `tenant` (MUST NOT)** — tenant narrowing is done by the `DomainPort` via `principal` / `capability` (§2.3 / §5). Storage without `tenant` support is fail-open (fixation is shared across tenants); full-scale storage isolation (RLS, etc.) is the product's responsibility.

**Session locale [Draft]**: the `session` object of `/compose`, `/compose/stream`, `/events`, and `/intent/normalize` MAY additionally carry `locale` (a language tag such as `"en"` / `"ja"`) (MAY). A host SHOULD thread it into `SessionContext.locale` (the reference implementation's `toSession`) so `SemanticPort.normalize` can use it as an NL hint (SHOULD). A host MAY further vary the generation output language per session (the reference implementation resolves a per-session `ComposePolicy` via `ComposeContext.policyFor`); **when it does, the language variation MUST be reflected in that policy's `generatorVersion` so caches separate per language (MUST)** — the cache key itself has no locale component, and an identical request (including `locale`) still maps to an identical cache key, so REST-CMP-002 is unaffected. **`NLQuery.locale` and `session.locale` carry distinct roles and are not interchangeable**: `NLQuery.locale` (an optional field of the `{input}` shape passed to `/intent/normalize` / `/compose`) is only an NL-normalization hint — when present it takes precedence over `session.locale` for that single purpose (the reference implementation's precedence is `input.locale ?? ctx.locale`) — while output-language selection (`ComposePolicy` / `generatorVersion`, above) and any fixation short-circuit's language gate are driven by `session.locale` alone; a per-call `NLQuery.locale` never substitutes for `session.locale` in either of those.

**Control-plane authorization [Draft]**: authorization of the audit/control-system routes (lineage / telemetry / promotions / fixations) is delegated to the host (only the confluence point of authorization is specified; it is not stated as a requirement). The reference implementation provides the optional hook `KohakuHostDeps.authorizeGovernance`; when wired, it makes an authorization decision before each request and returns a rejection as 403 `CAPABILITY_DENIED`. When not wired there is no authorization (the control plane is undefended), so in production it is the product's responsibility to protect it by wiring the hook or with external middleware. Conformance does not inspect this authorization (conformant even when unwired).

**Lineage forward paging [Draft] (design.md #53)**: `GET /lineage` MAY additionally accept `correlationId` (payload equality, alongside `intentHash` / `artifactId` / `specHash`) and, together, `order`, `cursor`, and `pageSize`. When `order=asc` is given, the host walks the lineage log exhaustively in append order instead of returning the default tail window, backed by the StoragePort's optional `pageLineage` method; the response shape is then `{events, nextCursor?}` (`nextCursor` an opaque string, present only when a further page exists) rather than the default `{events}`. `cursor` is opaque, obtained from a previous response's `nextCursor`; a request whose `cursor` does not decode to one this host issued is 400 `BAD_REQUEST`, as is an `order` value other than `asc`. A host whose storage does not implement `pageLineage` responds 501 `NOT_IMPLEMENTED` to a request carrying `order=asc`. A request that omits `order` is unaffected by any of the above: its shape and behavior remain exactly REST-LIN-001's.

### 6.1.1 Compose streaming [Draft]

A host MAY expose `POST /compose/stream` as Server-Sent Events (SSE) (MAY). The request body is identical to `/compose` (`{intent}` or `{input, session?}`). Its purpose is to shorten perceived initial-display latency: for slow generation paths (L1/L2), immediately return a skeleton (`ui.loading`), then send the diff to the finalized form (SpecPatch) after generation completes. When exposed, it satisfies the following — **the route itself is MAY, but if implemented, each requirement (REST-STR-001–003) is MUST for that implementation.** However, because the route is optional (MAY) and this profile is [Draft], [conformance/manifest.ts](conformance/manifest.ts) registers the three requirements as **SHOULD** and black-box-checks them (if unimplemented, the check is skipped and does not impair conformance; if implemented and violated, it appears in the report as a SHOULD warning). By this conditional norm of "MUST if implemented, SHOULD in the manifest," the (MUST) notation in the body and the manifest's `level: "SHOULD"` do not conflict:

- **REST-STR-001** (MUST): the first event is `event: spec`, with `data` = `{spec, capability, final, actions?}`. `spec` conforms to §2. If `final: true`, that is the final Spec (the fast path = cache hit / L0 / fixation short-circuit). If `final: false`, it is a skeleton, followed by `event: patch`. `actions?` (design.md #62/#64 [Draft]) is the same Governed Actions manifest described in §6.1 above; every `event: spec` payload carries it (computed from that event's own `spec`, so a `final: false` skeleton — which declares no write actions — naturally omits it).
- **REST-STR-002** (MUST): the result of `applyPatch`-ing the `event: patch`es in receipt order matches the `components` / `events` of the `POST /compose` Spec for the same intent (equivalence with the non-streaming path).
- **REST-STR-003** (MUST): the stream terminates with exactly one `event: done` (`data` = `{specHash, tier, cache}`) or `event: error` (`data` = `{error: {code, message}}`).

`patch` occurs 0..N times. The reference implementation sends zero or more **patches to a provisional Spec** assembled from the LLM's partial output during generation (only when `LlmPort.streamObject` is implemented; through parse & heal of the partial output — extracting completed components, pruning children, deferring events — it sends only in a form that always yields a §2-conformant Spec), and finally converges with a patch to the finalized form. The receiving side need only `applyPatch` in receipt order (each application result is always structurally validated = the equivalence of REST-STR-002 holds against the final form). Intermediate forms (the `final: false` skeleton, the provisional Spec, and the pre-application patches) MUST NOT be subject to caching, fixation, or lineage recording (MUST NOT) — these are done only against the final Spec. `capability` is issued exactly once in the initial `spec` event: for `final: true` (the fast path — cache hit / L0 / fixation short-circuit), it is issued **from the final Spec itself**, following the same rule as `POST /compose` (§5, including any `action.invoke` write scope the final Spec declares and the `DomainPort.listOperations()` intersection). For `final: false` (the skeleton), which has no `$ref` yet, it is issued read-only from all resolved QueryHandle URIs instead — `data.bind` is declared only on the final Spec and is not opened to L1/L2 generation, so a skeleton never carries bind variants or write scopes, and neither do the provisional Specs / patches that follow it (only a single-event `final: true` response can carry `action.invoke` over the stream).

A malformed body is returned as a normal 400 envelope before the stream starts. A generation failure after the stream has started cannot change the HTTP status, so it terminates with `event: error`. Reconnection is not defined (`fetch` + `ReadableStream` is assumed). Because the final Spec is cached, the retry strategy for a disconnection is the idempotent path that re-requests and returns in a single event.

### 6.2 MCP Apps profile (SEP-1865) [Normative]

- **MCPAPP-RES-001** The shared renderer is served as a `ui://` resource with `text/html;profile=mcp-app` (MUST).
- A tool declares its UI via `_meta` (MUST). The UI declaration is written in **both forms** — modern (nested `_meta.ui.{resourceUri, visibility}`; the norm since the SEP-1865 formalization on 2026-01-26) and legacy (flat `_meta["ui/resourceUri"]` / `_meta["ui/visibility"]`; backward compatibility for old hosts) (the values are identical; a host looking at either recognizes it as a UI tool).
- **MCPAPP-APP-001** The bulk-data, event, and write tools (resolve_binding / event / action) are set to `_meta["ui/visibility"] = ["app"]` (and the same value in modern's `_meta.ui.visibility`) and made invisible to the model (MUST) — bulk data is not passed through the model's context, and writes (action) fire only from a capability-bearing widget (iframe).
- **MCPAPP-FBK-001** The result of a UI-bearing tool includes a non-empty text fallback in `content[0]` (MUST).
- **MCPAPP-CAP-001** The result of a compose-family tool call (`${prefix}_compose` / the generated intent tools / `${prefix}_event`) carries the Spec in `structuredContent.spec` and the capability token in `_meta["kohaku/capability"]` (MUST). `structuredContent` MUST NOT also carry the capability token (MUST NOT) — `_meta` does not enter the model's context while `structuredContent` does, so keeping the bearer write token out of `structuredContent` closes the path where a host that does not honor `${prefix}_action`'s app-only `_meta["ui/visibility"]` hint (or a prompt-injected instruction) could otherwise have the model itself read the token and drive a write with an arbitrary payload.
- The shared renderer resource explicitly declares csp with an empty allowlist (`{connectDomains: [], resourceDomains: [], frameDomains: [], baseUriDomains: []}`) on the **resource-side** `_meta.ui` (SHOULD) — because it is a single-file bundle + bridge-mediated data fetch, it needs no external origin whatsoever, telling the host it may apply the strictest sandbox. csp / permissions cannot be placed on the tool-side `_meta.ui` (SEP-1865; the tool side has only `resourceUri` / `visibility`). It is placed with the same value in both resources/list (resource description) and the contents of resources/read (SEP-1865 prefers the contents side).
- **mcp-ui legacy UIResource co-listing** (optional, off by default): for hosts that do not support SEP-1865 and render only mcp-ui's UIResource (detected by the `ui://` prefix), the compose-family tool result MAY append `{type:"resource", resource:{uri:"ui://kohaku/view/<intentHash>", mimeType:"text/html", text:<self-contained snapshot HTML>}}` to `content[]` (MAY). The text fallback in `content[0]` (MCPAPP-FBK-001) is unchanged. The snapshot is a static display (no interaction or recomposition), and an assembly failure is swallowed, falling back to a normal response without co-listing (fail-open). Because it becomes about 1MB/result, do not enable it on modern hosts.
- A widget MAY, after an interaction (recomposition / write via app-only tools), feed back **only the summary text of the current view** to the model context via `ui/update-model-context` (MAY; only when the host declares the capability). It does not carry bulk data (the principle of §4.3 is unchanged). It is not sent on the first tool-result (content[0] is already model-visible — avoiding double injection).
- Rendering of an L2 (sandbox.html) node on the mcp-app surface is unsupported in v0.1 and is substituted with a text fallback (MCPAPP-FBK-001). A host MAY wire a `ViewRecorder` into the MCP profile (the reference implementation's `McpHostDeps.recorder`) the same way the REST profile does (§6.1) (MAY); when wired, `view.composed` and `view.fallback` are recorded around every compose-family tool call and `view.interacted` around `${prefix}_event` (before recomposing), matching the REST profile's recording points. When unwired, none of the three are recorded.
- The direct write path is supported in v0.1 as the app-only tool `${prefix}_action` (default `kohaku_action`) (symmetric to REST's `POST /binding/action`; one of the MCPAPP-APP-001 app-only tools). The input is `{action, payload?, capability}`, the capability is validated with **write** scope (`{kind:"write", ref:action}`), and the response `structuredContent` is `{result, invalidates?, refVersions?}` (`invalidates` / `refVersions` appear only when the side-effect declaration (`actionEffects`) is wired; when unwired, only `{result}` = backward compatible). The write loop (ActionResult / invalidates / refVersions) is supported by both REST and MCP. `kohaku_resolve_binding` remains read-only as before.
- **MCPAPP-ACT-001** `${prefix}_action` MUST enforce §5's Governed Actions requirements (ACT-PRM-001 / ACT-APR-001) identically to REST's `POST /binding/action` — the same params-schema validation and tier gate, against the same `DomainPort` configuration, for the same action — expressed as a structured tool error rather than an HTTP status: `${prefix}_action`'s input additionally accepts optional `confirmed` / `approval` fields (mirroring the REST body), and a gate failure returns `isError: true` with `structuredContent.error` shaped `{code: "ACTION_PARAMS_INVALID", issues}` or `{code: "APPROVAL_REQUIRED", approval: {requestId, action, tier, payloadHash}}` (the same two field shapes §6.1's REST error envelope carries) (MUST). The compose-family tool result (`${prefix}_compose` / the generated intent tools / `${prefix}_event`) MAY additionally carry the Governed Actions manifest in `_meta["kohaku/actions"]`, the MCP equivalent of §6.1's `actions?` field, placed in `_meta` rather than `structuredContent` for the identical reason MCPAPP-CAP-001 keeps the capability token there (operational detail for the widget's own client-side pre-check, not model-visible content).
- **Tool locale [Draft]**: every UI-producing tool (compose / render_snapshot / the generated intent tools / event) MAY additionally accept an optional `locale` argument (a language tag such as `"en"` / `"ja"`) (MAY) — the calling model sets it to the user's environment/conversation language per call. A host SHOULD map it onto the compose session's `SessionContext.locale` (SHOULD), the same knob the REST profile carries as `session.locale` (§6.1 "Session locale"), so NL normalization, any fixation gate, and a per-session `ComposePolicy` (output language) all see it. The argument name `locale` is **reserved**: it never enters the canonical intent params (intent-hash stability), and an intent that declares a param of that name is rejected at registration time.
- **MCP core protocol version [Draft]**: this profile's normative MUST/SHOULD requirements above assume the **2025-11-25** MCP core wire protocol (stateful sessions, `initialize`/`initialized`, results without a `resultType` field). A conforming host MAY additionally be reachable over the later 2026-07-28 protocol version; this profile has forward-adopted its purely additive items ahead of a full transport-level migration — every tool result carries `resultType: "complete"` (a host on the 2025-11-25 wire treats the field's absence, and a 2026-07-28-aware host its presence, identically per that changelog's own compatibility rule), and a tool call's `_meta.traceparent` (SEP-414), when present and well-formed, is used to correlate observability records with the caller's own trace. Neither item changes any MUST/SHOULD above or requires a client to be 2026-07-28-aware. The Python reference implementation additionally stamps `ttlMs`/`cacheScope` (`CacheableResult`) on `tools/list` and `resources/list` results where its SDK offers a clean hook to do so (not on `resources/read`, and not yet on the TS reference implementation — see the migration plan below for why). The session-removal, `server/discover`, and MRTR items of 2026-07-28 are not yet adopted (implementation status: see `docs/design.md`'s "MCP 2026-07-28 / SDK v2 migration plan").

### 6.3 A2UI profile [Draft]

A profile that maps UISpec / SpecPatch onto A2UI (adjacency-list declarative UI messages). The default target is **A2UI v0.9.1** (the current stable version at a2ui.org). An **opt-in `target: "v1.0"`** additionally follows the **A2UI v1.0 RC** (still targeting a Q4 2026 stabilization per a2ui.org; not yet stable) — see "v1.0 RC target (opt-in)" below. The reference implementation is `packages/host-a2ui` (`toA2ui` / `patchToA2ui` / `fromA2uiEvent` / `serializeA2uiLines` for the outbound direction; `fromA2ui` / `createA2uiIngest` / `toA2uiClientAction` for the inbound direction — see "Inbound A2UI (ingest) [Draft]" below). **Because it is Draft, it is out of scope for conformance checking** (§7).

The envelope is `{ "version": "v0.9.1", "<messageKey>": {…} }` (exactly one message key). Components are the flat form `{id, component: "Text", …props inline, children | child, action?}`. Streaming is JSONL (one message per line; `serializeA2uiLines`). **Default output (`target` omitted or `"v0.9.1"`) is byte-identical to prior versions of this profile**, fixed by a golden test (`packages/host-a2ui/test/a2ui.test.ts`, "target v0.9.1 (default) output is byte-identical to pre-v1.0 output").

**Design principle (revised to follow v0.9.1)**: A2UI v0.9.1 is strict (components are `unevaluatedProperties: false`; messages forbid extras) and **cannot carry `x-kohaku-*` extension keys on the wire**. Therefore the wire is kept v0.9.1-compliant, and kohaku-specific information (pass-by-reference `data.$ref`, `data.bind`, `visibleWhen`, intent, provenance, dataVersion, refVersions, state, events, original type) is **losslessly offloaded to a sidecar (`KohakuSidecar`; a separate structure outside the wire)**. `toA2ui` / `patchToA2ui` return `{ messages, sidecar }`, and a kohaku-aware client can fully restore from the sidecar.

Correspondence table:

**Default output is unaffected**: `target` omitted, or `target: "v0.9.1"` explicitly, produces byte-identical output to the pre-v1.0 profile (golden-tested).

#### Inbound A2UI (ingest) [Draft]

The reverse direction: kohaku as the *renderer* client of a **third-party** A2UI agent, rendering its surface inside kohaku's own UI and routing interactions back out. Reference implementation: `packages/host-a2ui/src/inbound/` (`schemas.ts` / `reduce.ts` / `from-a2ui.ts` / `ingest.ts` / `to-a2ui-client-action.ts`). **Like the rest of §6.3, this is out of scope for conformance checking** and registers no MUST/SHOULD requirements.

The inbound wire (both v0.9.1 and the v1.0 RC's `createSurface`/`updateComponents`/`updateDataModel`/`deleteSurface`) is validated strictly (unknown envelope/structural keys rejected; a component's catalog-inlined props stay open-ended) and folded into a `SurfaceState` (a per-surface map of `{id -> component}` plus the accumulated data model), then converted to a `UISpec` by `fromA2ui`. This is **not** the exact inverse of `toA2ui`: a genuinely third-party surface carries no `KohakuSidecar`, so the conversion is best-effort and potentially lossy — only a surface that *is* kohaku's own prior `toA2ui` output, re-ingested with its sidecar **and an explicit `trust: "trusted"`**, restores losslessly (component-by-component, via the sidecar, including its original events). `trust` defaults to `"untrusted"`, under which any supplied `sidecar` is ignored entirely — see "Security: write-action forwarding" below for why this default matters, not just for fidelity.

**Security: JSON Pointer / component id safety.** `updateDataModel.path` and a component's `id` are both untrusted, agent-chosen strings that this profile's internal object-graph walk (`reduce.ts`'s `setAtPointer`/`getAtPointer`/`deleteAtPointer`/`upsertComponents`) would otherwise use as plain object keys. A path segment or id of `"__proto__"` is not an ordinary property name on an ordinary object — bracket-assigning it *reassigns that object's own prototype* instead of storing data, producing a `dataModel` whose injected value is invisible to `canonicalStringify` (own-enumerable-only, so `dataVersion` hashes it identically to the unmodified data model — a cache-key collision) yet readable back through a plain property lookup (which walks the prototype chain) — the same cache key silently serving different content. `"__proto__"`/`"constructor"`/`"prototype"` are rejected outright wherever they would become a key (a schema-validated component `id`, or a `path` segment — the whole message is rejected), and, independently, every object this profile itself constructs from such input is built with `Object.create(null)` and read/written via `Object.hasOwn` checks, so no property lookup here ever falls through to an inherited `Object.prototype` member (whether from a reserved name or an unrelated one, such as `"toString"`) regardless of the key.

**Security: DoS bounds.** A schema-valid inbound message has no inherent upper bound on how expensive it is to process. Two independent caps close this: JSON nesting depth (`updateDataModel.value`, and a whole component's combined catalog props / `action` / nested function calls in one measurement — checking each nested sub-schema independently would *under*-count the true depth from the component's own root, since each would restart its own count at 1) is capped at spec-core's `MAX_JSON_OBJECT_DEPTH`; and `createA2uiIngest` caps a single `ingest()` call's message count, a surface's accumulated component count (checked cumulatively across every call, not just the current one), and the data model's serialized size (`JSON.stringify(...).length`) via `maxMessagesPerIngest` / `maxComponentsPerSurface` / `maxDataModelSizeBytes` (all overridable; conservative defaults of 1000 / 2000 / 1 MiB). Those per-field checks alone are not sufficient: they run inside a `.superRefine`, i.e. only *after* zod has already recursively descended through the mutually-recursive value schemas to validate everything beneath that field, so a sufficiently deep (but schema-cheap) raw message can exhaust the JS call stack during that descent itself, before any `superRefine` runs. `parseInboundA2uiMessage` therefore also runs a stack-safe depth check directly against the **raw, not-yet-validated** message before calling into zod at all, at a looser limit (`MAX_JSON_OBJECT_DEPTH` plus a fixed allowance for the legitimate envelope/component wrapping around a depth-guarded field) that only has to stay safely below the depth at which zod's own recursion becomes risky, not enforce the precise per-field rule.

**Loss policy** (`FromA2uiOptions.unmappable`, default `"fallback"`): four kinds of "cannot represent" — an unknown component type, a data-bound repeated template (`{children: {path, componentId}}`, which also covers a data-bound table/chart-style widget, since the RC facts note records no other data-binding mechanism for repetition), and a computed function-call *value* (as opposed to an `action.functionCall`, handled above) — replace the *whole* offending component with a deterministic `presentMarkdown` placeholder and record the loss; `"reject"` instead throws, failing the whole conversion. A `"binding-snapshotted"` loss is never subject to this policy (a snapshot is always representable, just not live). **No LLM is ever called** for any of this. The converted Spec is run through `validateSpecStructure`; any error-severity issue (e.g. a genuinely malformed reference) also fails the conversion rather than shipping a broken Spec.

**Intent derivation** (`createA2uiIngest`): a caller SHOULD pass an explicit `{canonical, params}` Intent per surface. Without one, the default canonical name is `a2ui.<agent_slug>.<surface_slug>` (params `{agent, surfaceId}`) — since a real agent's `surfaceId` is typically unique per session/connection, this default rarely repeats and the Spec cache rarely hits (see `packages/host-a2ui/README.md`'s "governance proxy" section). `agentId` always comes from the caller's own authentication, never from message payloads.

**Provenance**: `tier: "L1"`, `composedBy: "a2ui-ingest"`, `model: "a2ui:<agentId>"`, `cache` one of `"miss"` / `"hit"` / `"fixated"` (never `"bypass"` — there is no equivalent of composer's bypass path here). The cache key is spec-core's `cacheKey({intentHash, dataVersion, generatorVersion: "a2ui-ingest/<agentId>"})` with a tenant segment appended when a tenant is given; `dataVersion` defaults to a truncated hash of the canonical data model. A fixation (`storage.getFixation`) is checked before any conversion work, mirroring host-core's fixation shortcut, and short-circuits to `cache: "fixated"`.

**Security: write-action forwarding.** spec-core's `resolveWriteActionName`/`collectWriteActions` — what a host uses to decide which write capability to issue for a Spec — resolve a write action's name from, in order, the firing component's `props.action` then the firing `EventBinding`'s `payload.action`. An A2UI `action.event`'s `context` is a wholly agent-controlled, schema-open dictionary (§6.3's `A2uiEventSchema`), so a third-party agent could otherwise set `context: {action: "someRealOperation"}` and have a host mint a write capability for a domain operation it was never authorized to name — the same is true of a component's own props, if they were ever copied through unfiltered. `fromA2ui` closes this two ways, unconditionally (not gated by `trust`, since a sidecar-restored component never reaches this logic at all — see above): every synthesized event's `payload.action` is always the fixed sentinel `A2UI_FORWARD_ACTION` (`"a2ui.forward"`), with the agent's actual event name/context nested under `payload.event`/`payload.context` instead (out of `resolveWriteActionName`'s reach); and the wire's own `action` key is a reserved structural field (`A2uiComponentAction`, not a plain string), so it can never end up copied into a component's kohaku-side `props`. **A host serving an ingested Spec MUST recognize `A2UI_FORWARD_ACTION` and route it to `toA2uiClientAction` before ever considering dispatching to its `DomainPort`, and MUST NEVER register `A2UI_FORWARD_ACTION` itself as a real operation** — doing so would let any ingested (third-party) content trigger that operation directly.

`toA2uiClientAction` is the reverse of `fromA2uiEvent`: given the `GuiAction` a user interaction with an ingested surface produces, it reads the forwarded event name/context from `params.event`/`params.context` (throwing if `params.action` is not `A2UI_FORWARD_ACTION` — calling it on an unrelated `GuiAction` is a host wiring bug) and returns `{action: {name, context}}` (the RC facts note's renderer→agent shape, deliberately minimal — no `surfaceId`/`sourceComponentId`/`timestamp`, which the note calls transport-dependent; **verify against the A2UI v1.0 spec** if a concrete transport needs them threaded back in).

## 7. Conformance [Normative]

The machine-readable requirements are in [conformance/manifest.ts](conformance/manifest.ts) (37 MUSTs; of these, **SPEC-STA-001** checks, in the self suite, the version declaration and reference integrity of state / visibleWhen / state.set, and **SPEC-STA-002** checks the version declaration and initial-variant integrity of `data.bind` (no BIND_* errors). bind is [Draft], so it is not listed in the REST black-box manifest). **SPEC-ENV-003** (theme independence), **SPEC-EVT-002** (Renderer prohibition on forwarding undeclared events), **SPEC-DATA-002** (per-reference version reconciliation via `refVersions`; §2.3), **CMP-DET-001** (the general form of composition determinism), **CMP-DET-002** (an L2-only cache is never returned to a session with L2 disallowed; design.md #70), and **CMP-GEN-001** (§4's `data.$ref` QueryHandle-set constraint on generated components) are documentary norms in the body; each is listed in the manifest with `verification: "reference"` and guaranteed by the reference implementation's package tests (`verifiedBy` — the first three are also §7.1's renderer conformance checklist) rather than checked directly by the black-box suites (determinism against a REST host is additionally checked directly by the black-box **REST-CMP-002**). **ACT-PRM-001** / **ACT-APR-001** (§5's Governed Actions params-validation and approve-tier requirements) and **MCPAPP-ACT-001** (§6.2's REST/MCP equivalence for the same) are likewise `verification: "reference"` — action names and `paramsSchema`/`tier` shapes are `DomainPort` configuration a generic conformance host has none of, so these are guaranteed by the reference implementation's own package tests (`packages/host-rest/test/binding-action-gate.test.ts`, `packages/host-rest/test/approvals.test.ts`, `packages/host-mcp-apps/test/mcp.test.ts`'s governed-actions cases, and their Python mirrors) rather than checked black-box against an arbitrary host's own action set — the same reasoning **REST-RL-001** (rate limiting) already applies for an equally host-configuration-dependent feature. **ACT-CNF-001** (confirm-tier, SHOULD) and **LIN-ACT-001** (action audit events, SHOULD) do not change the MUST count.

Each requirement has two verification categories (`verification`). **blackbox** are requirements the conformance suite (self / REST black-box) checks directly with only the baseUrl (`SPEC-*` / `REST-*` / `LIN-PRM-001`). **reference** are internal invariants unsuited to black-box checking (`MCPAPP-*` / `SBX-*`, and the six documentary norms above), guaranteed by the reference implementation's package tests (the manifest's `verifiedBy`). The report displays reference requirements as "guaranteed by reference-implementation tests (out of black-box scope)," distinguished from black-box unchecked ones (`notCheckedMustIds` not checked by another profile) — to preserve the difference in meaning between the former (already guaranteed) and the latter (out of scope for that suite). A result can also be flagged **not checked** at run time rather than only "out of this suite's scope": **LIN-PRM-001** reports this way when `GET /lineage` itself is unreachable/erroring (as opposed to reachable with zero `component.published` events, which is a vacuous pass) — such a result is excluded from the pass/fail tally (it is neither a false pass masking an unreachable dependency nor a fail that blocks CONFORMANT on an optional precondition) and is folded into the same `notCheckedMustIds` reporting path, carrying its own reason instead of the generic "not checked" text. The verdict line then reads `CONFORMANT (N MUST not checked)`. Run:

```bash
node cli/bin/kohaku.js conformance --self                                   # Spec-format self check
node cli/bin/kohaku.js conformance --rest http://localhost:8787/api/kohaku # REST-host black-box check
```

An implementation that satisfies all MUST requirements is conformant. SHOULD violations appear as warnings in the report.

Of the [Draft] / [Reserved] profiles, **§6.3 A2UI** is out of scope for conformance checking and lists no requirements in the manifest — so as not to fix black-box requirements before the spec is finalized. However, **§6.1.1 Compose streaming is an exception**: though [Draft], it registers REST-STR-001–003 in the manifest as **SHOULD** and checks them in the REST black-box suite (SHOULD rather than MUST because the route itself is MAY; skipped if unimplemented, a SHOULD warning if implemented and violated; see the conditional norm in §6.1.1). This reflects the judgment to keep regression-detecting the wire shape (leading `event: spec` / equivalence of `event: patch` / single termination) even while Draft.

### 7.1 Renderer conformance checklist [Normative, reference]

Because a renderer is not a REST host (it cannot be black-box-checked by baseUrl), **no new blackbox manifest requirement is added.** Any renderer implementation (including the reference `renderer-react` / `renderer-wc`) SHOULD satisfy the documentary norms below. In the reference implementation these are guaranteed by **reference tests** (package tests) — specifically, unit tests of `renderer-core`'s shared pure functions (`resolveEmit` / `resolveBoundRef` / the presenters) and the React ⇄ WC **parity harness** (the semantic-DOM-equivalence corpus + the shared-event-behavior corpus + the axe accessibility corpus; `packages/renderer-wc/test/parity`) act as gatekeepers.

| Norm | What the renderer must satisfy | Reference-test guarantee |
|---|---|---|
| **SPEC-EVT-002** | Forward upstream only the `on`s declared in the Spec's `events`, and discard undeclared events. `state.set` is self-contained within the Renderer and is not emitted upstream (to the server). | the parity event-behavior corpus (undeclared drop / declared forward yield the same `onEvent` arrival sequence in both renderers) + the `resolveEmit` unit test of `renderer-core` |
| **SPEC-ENV-003** | The Spec is theme-independent. Tokens (`ThemeTokens`) are resolved on the Renderer side, and the Spec structure carries no colors or dimensions. | the parity structure corpus (both renderers inline-expand the same tokens for semantic DOM equivalence) |
| **SPEC-STA-001** | The semantics of client-local state (`spec.state`) — `visibleWhen` evaluation, local update via `state.set`, and re-initialization tracking `intent.hash`. | the parity state.set → visibleWhen DOM-appearance corpus + the SpecStateStore unit test of `renderer-core` |
| **SPEC-DATA-002** | Reconcile the version of pass-by-reference data per reference (`refVersions[ref] ?? dataVersion`), and reconcile the re-resolution of the write loop on the event's version (skip reconciliation if unknown). A1's `$state`-derived variants are not reconciled. | the parity A1 bind re-resolution / write-loop corpus + the BoundDataController unit test of `renderer-core` |
| **SPEC-A11Y-001** (SHOULD) | Every generated component's DOM SHOULD pass axe-core's structural accessibility rules (ARIA attribute/role validity, name/role/value semantics, labels, heading order, table headers, form-control labeling) in both renderers. Rules whose verdict depends on real visual layout (`color-contrast`, `target-size`, …) or on page-level document/landmark structure are out of scope for a fragment-scoped renderer check (they belong to the host page, not to an individual component) and are excluded — see `packages/renderer-wc/test/parity/axe-config.ts` for the exact exclusion list and rationale. | the parity axe a11y corpus (`packages/renderer-wc/test/parity/a11y.test.ts`), run against both renderers over the same golden Spec corpus as SPEC-ENV-003 |
| **SPEC-DISC-001** (SHOULD) | A renderer that surfaces AI-generation disclosure to the end user (design.md #66) SHOULD derive it entirely from `provenance` (`tier` / `cache` / `fallback`) rather than from any dedicated field — the Spec format itself carries no disclosure field, so a host cannot forget to strip a stale one on demotion and a renderer cannot trust a value baked into the payload by an untrusted party. The derivation: `fallback` present → not disclosed (a deterministic degradation, not model output, regardless of tier); tier `L1`/`L2` → AI-generated; tier `L0` with `cache: "fixated"` → AI-assisted, human-reviewed; otherwise → not disclosed. Disclosure defaults to off (opt-in). | the `deriveDisclosure` tier × cache × fallback table (`packages/renderer-core/test/disclosure.test.ts`), `SpecView`'s `disclosure` prop (`packages/renderer-react/test/disclosure.test.tsx`), and the `<kohaku-surface disclosure>` parity corpus (`packages/renderer-wc/test/parity/disclosure.test.ts`) |

The visual rendering of `chart` does not require pixel parity across renderers (the reference implementation renders differently with Recharts and inline SVG). However, the content of the a11y alternative (a visually hidden data table) must be semantically equivalent (guaranteed by the parity chart semantic-equivalence test).

Unlike the four MUST norms above, **SPEC-A11Y-001 and SPEC-DISC-001 are SHOULD**: a renderer failing either does not fail conformance, but is expected to converge on it. Neither changes the manifest's MUST count (§7).

## 8. Promotion and Lineage [Normative]

- Promotion state machine: `in_use → candidate → judging → in_review → approved → schema_proposed → published` (+ judge_failed / changes_requested / rejected / withdrawn). Transitions are governed by the transition table in [packages/lineage/src/promotion/machine.ts](../packages/lineage/src/promotion/machine.ts).
- **Withdrawal (unpublish)**: `published → withdrawn` is allowed only via the dedicated action `unpublish` (≠ `withdraw`). The destination does not create a new state but reuses `withdrawn` — because `artifactId` derives from sha256 (of the content), re-publishing the same artifact would mean "the same thing" for auditing, so re-publishing correctly goes through a new artifact. The `withdraw` action continues to reject terminals (published/rejected/withdrawn) (the structural guarantee of LIN-PRM-001 and existing transitions are unchanged). Unpublish runs in the order snapshot authority → audit → projection removal (mirroring publish's snapshot-first order), so its `onUnpublish` side effect (removing the promotion from the catalog/Intent, implemented by the product) always runs after `withdrawn` is durable and `component.withdrawn` (recorded with `from:"published"` to distinguish it from pre-promotion withdrawal) is on the log; `onUnpublish` MUST be idempotent, because startup `reconcile` re-applies it to any non-published snapshot whose candidate still has a persisted draft, converging a projection removal that failed partway. Because the catalog fingerprint changes, a cache containing a promoted component is not "deleted" but "made unreachable," and a fixation containing that component is caught later by the staleness detection of §8.
- The candidacy threshold, the judge's passing score, and blocking-ness are variable as policy. However, human review (LIN-PRM-001) is invariant.
- Lineage events are append-only and carry `{id, ts, actor{kind: user|model|system}, type, payload}` (MUST). Under multitenancy, a record MAY be stamped with an optional `tenant` (MAY) and narrowed by `LineageFilter.tenant` (unspecified = all records = legacy behavior; old events without a recorded `tenant` appear only under an unspecified filter). Promotion aggregation (`evaluateAndList` / `list`), fixation proposals (`proposals`), and fixation (`fixate` / `getFixation` / `listFixations` / `deleteFixation`) can be done tenant-scoped. Storage without `tenant` support is fail-open (fixation is shared across tenants).
- Fixation (L1→L0) fixes only the structure, and data is always kept fresh by `$ref` pass-by-reference (MUST). Serving a fixated Spec displays `provenance: {tier: "L0", cache: "fixated"}`.
- **A Spec carrying `provenance.fallback` and a tier-`L2` result MUST NOT be fixated (MUST NOT)** — a fallback is a generation failure or a capability-negotiation downgrade rather than the intended structure, and L2 is free-form, sandbox-only generation the promotion pipeline (not fixation) governs; pinning either as L0 would freeze a broken or ungoverned structure as the permanent fast path. The reference implementation rejects both at `/fixations/approve` (422 `COMPOSE_FAILED` for a fallback result, 400 `BAD_REQUEST` for an L2 result).
- **Fixation staleness detection** (SHOULD): a fixated Spec (`pinnedSpec`) is the structure as of fixation time, and if the catalog (component types/props) changes afterward, it may keep serving a broken structure. A host SHOULD inspect for staleness before serving. The reference implementation adopts a "fingerprint fast path + deferred revalidation + self-healing" scheme:
  - A fixation record retains the **catalog fingerprint** as of fixation time (`catalogFingerprint`, optional = compatible with old records).
  - If it matches the current catalog fingerprint, the structure is deemed unchanged and served without revalidation (**fresh**).
  - On mismatch/absence, the `pinnedSpec` is revalidated against the current catalog. If it passes, it is served, the current fingerprint is re-stamped, and it goes on the fast path thereafter (**revalidated**). Old records migrate naturally via this path (no migration script needed).
  - If validation fails, the fixation is not served (**stale**), the fixation is invalidated as self-healing (`intent.unfixated` recorded with `actor: {kind:"system"}` and `reason: "stale"`), and it falls back to normal compose. A failure to invalidate does not stop serving (a degraded operation in which the fixation remains and each time revalidation fails → fallback).
  - Even a fixation that passed the catalog-fingerprint decision (fresh / revalidated) has its **set of resolved reference URIs** reconciled before serving. If the reference-URI set the fixated Spec represents (the key set of `refVersions`; for old records without `refVersions`, the set of `data.$ref` of the pinned components) does not match the URI set of the current Intent's `resolveQuery` resolution (addition/removal/replacement of URIs), it is deemed **stale**, and the fixation is likewise invalidated and falls back to normal compose. Because the catalog fingerprint derives from component types/props and is independent of the query mapping, even for the same Intent, if the reference set drifts due to a code revision or a change in the semantic layer, fresh / revalidated cannot catch it. Serving it drifted would break per-reference version reconciliation (`refVersions` / SPEC-DATA-002) (a removed reference always shows STALE, an added reference shows freshness with no corresponding component), so it errs on the safe side.
  - The Spec/trace of the fresh path is identical to the current one (does not affect determinism checks such as `REST-CMP-002`).
- **Catalog migration** (design.md #65): a catalog entry marked `deprecated` with a `replacedBy` (§3.1) still validates for a fixation referencing it (deprecation does not by itself make a fixation **stale** under the staleness detection above), but a host SHOULD migrate such fixations onto the replacement before the entry's `sunset` date. After `sunset`, a host MAY remove the entry from the catalog entirely, at which point every remaining reference becomes **stale** (revalidation now fails with `UNKNOWN_TYPE`) and is self-healed exactly as above. A migration rewrite is recorded as `intent.migrated` rather than `intent.fixated` — the fixation's identity (`intentHash`) and tenant are unchanged, only its pinned structure and `structureHash`. The reference implementation's `Fixations.replace` records it with the human approver as actor and payload `{intentHash, structureHash, approver, planId?}`, guarded (TOCTOU) against the fixation having moved on since the migration was planned; the `kohaku migrate plan`/`apply` CLI drives it in bulk across every fixation referencing a deprecated-with-replacement type.

12. `StoragePort` concurrency contract clarified: serializing the read-modify-write of a given (tenant, key) is the **host's** responsibility (single-writer per process; running multiple instances against the same backing store is out of scope). Two additive hooks narrow one specific race under that contract — `putFixation`'s optional `options?: { ifPresent? }` (skip the write unless the key already exists; used by self-healing's `refreshFingerprint` so it cannot resurrect a fixation another writer deleted) and `FixationRecord.revision?` (a per-write token, monotonic within a process, finer-grained than `fixatedAt`'s ms-precision timestamp; `invalidate`'s TOCTOU guard prefers it when present, falling back to `fixatedAt`). Both optional and additive; a `StoragePort` or fixation record that predates them keeps the prior behavior unchanged.
13. Added two optional `provenance` fields (both MAY, pairing with item 7's `generatorVersion` cache-key component): `generatorVersion` (the host's generator identity in effect at composition time) and `kit` (`{id, version}`, the design kit the generated markup was written against). Both are stamped by the composer only when the corresponding `ComposePolicy` field is set, on every tier (including L0) and preserved as-is on a cache hit (the composed-time value, not the surface's current kit) and across L1→L0 fixation (spread from `pinnedSpec.provenance`). Neither participates in `policyFingerprint` or the cache key itself (provenance is excluded from `computeStructureHash`, so this does not affect fixation's structural-stability judgment; `computeSpecHash` changes for newly composed Specs only). **SPEC-KIT-001** (SHOULD) lets a surface that injects a design-kit stylesheet detect a version mismatch against `provenance.kit` instead of rendering unstyled markup silently — checked fail-open (a mismatch is reported via telemetry, never blocks rendering) by the reference sandbox (`mountSandbox`'s `provenanceKit` comparison).
14. Catalog migration contract (design.md #65): `ComponentDefinition.deprecated?` (§3.1: `{reason, since?, replacedBy?: {type, version?}, sunset?}`) marks a part superseded — generation stops offering it (`selectGenerationTypes`) while validation of already-fixated Specs keeps passing, and the catalog fingerprint folds in a `!deprecated` suffix per such entry (§3.3). `FIXATION_EVENT_TYPES` gains `intent.migrated` (§8), recorded by `Fixations.replace` when a migration rewrites a fixation's `pinnedSpec` in place. Both additive: a catalog with no deprecated entries and a fixation store with no `intent.migrated` events are byte-identical to before this item existed.
